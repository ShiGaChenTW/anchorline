## ⚠️ 下一步：Wave 3（規格未拍板，不要直接開工）

### R1 —— agent 的修改建議要能自動套用

**Scott 2026-08-26 最後一問：「AI 結構審查做完後，所提出的修改建議能自動修復嗎？」
答案是現在不行**，已當面回覆：

- AI 結構審查是 `review` 關卡（`seed.ts:366`，`kind: "review"`），產出只釘在
  `CaseStage.agentResult`，**完全不碰 PRD 內文**
- 唯一會動內文的是 `edit` 關卡，而它做的是「把 agent 的**整段原始輸出**覆寫進
  **一個**指定欄位」，還要人按「存進文件」—— 那不是「依建議修好」

**地基風險（比功能本身重要）**：agent 現在回自由散文，那是給人讀的，機器套不上去。
要自動修就得先讓它穩定回**結構化結果**（sectionId / fieldKey / 新內容）。

**已向 Scott 提出的架構岔路，他尚未選**：

- **A 一次到位** —— 改審查 prompt，出意見的同時給改好的內容
- **B 兩段式（Miles 建議）** —— 審查維持只出意見；另加一顆「套用建議」，
  把意見 + 現在的 PRD 再餵回模型要結構化修改。三個理由：
  1. 審查更誠實（同一次呼叫要它既批評又重寫，模型傾向把批評講輕）
  2. 失敗有退路（解析壞掉還留得住可讀的審查意見；A 會整關卡死）
  3. 它是選用的（看完建議再決定要不要讓它動手）

**建議的第一步：只驗地基。** 讓 agent 對真實 PRD 產出結構化修改，量它穩不穩、
格式壞掉的比例多高。那一步做完才知道 R1 值不值得投。

⚠️ R1 兩種架構都會踩到母規格明寫的「不做：逐條勾選套用的 diff UI」，要重新拍板。

## 這輪學到、值得帶走的五件事

1. **要求 agent 邊做邊把結論寫進 repo 內的檔案。** 這輪七個 agent 幾乎全在交付後
   直接斷線，兩個一句回報都沒有 —— 工作沒掉的唯一原因就是這條。
   **但它保得住已完成的工作，保不住未執行的指令**：有一次指令完全沒被執行，
   是回頭 grep 檔案才發現。**每一則指派都要回頭查檔案，不看回話。**
2. **source-grep 型測試的解析度到「函式」為止。** 它擋得住 Wave 1 的 F0
   （新參數只有測試在傳），但 C-1／C-3／送審預檢這三條缺陷都在**函式之間**，
   測試全綠。要抓那種形狀，得把順序抽成純函式再餵時序替身 ——
   `dialog-flow.ts` 與 `submit-flow.ts` 都是為此而生。
3. **文案與行為對不上，不管往哪個方向錯都是同一個缺陷。** 這輪犯了四次。
   解法固定下來了：**雙向合約測試** —— 先跑 store 證明行為做到了，
   才允許斷言文案講那句話。
4. **最有價值的缺陷是使用者第一眼撞到的那個。** 「畫面沒有改」與「跟主線沒有差異」
   兩條，當時 tsc、1700+ 測試、跨 context 審查、實機安裝全綠。
   共同點：**沒有任何一條測試同時持有兩邊**（畫面顯示什麼 vs 送審會建立什麼；
   預檢說可以 vs commit 真的放不放行）。
5. **不要採信 agent 的自述。** 這輪至少三次自述與磁碟不符：一次說做了其實沒動、
   一次 HEAD 資訊過期、一次說「兩條測試都變嚴」而其中一條的 grep 其實放寬了
   （雖然有更強的行為測試補償）。**每次都自己跑 tsc / bun test / vite build，
   並逐行讀 diff。**
