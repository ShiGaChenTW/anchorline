    怎麼用這一頁

    判準只有一句：這件事改不改「對外承諾」？ 改了走新功能，沒改但行為不對走 Bug，兩者都不是就是維護。

    什麼時候用 PRD 說的話要跟著改 —— 新增能力、改變驗收條件、擴大或縮小範圍。

    會產生 openspec/changes/<id>/ 底下 4 份：proposal · spec · design · tasks

    1. 先改 PRD，不是先開 change。 承諾變了就先讓 PRD 反映，否則 change 會描述一件 PRD 沒說過的事， 之後看紀錄的人對不起來。
    2. 在這一頁建立並下載，把 4 份文件放進 openspec/changes/<id>/。
    3. proposal.md 一定要寫 Non-goals。 這是這個 repo 的 openspec/config.yaml 明訂的規則 —— 範圍沒有邊界的提案會在實作中無限膨脹。
    4. specs/<id>/spec.md 寫 Requirement 與 Scenario， 用 ## ADDED / MODIFIED Requirements 標明是新增還是修改。
    5. design.md 只在有技術取捨時才寫。 沒有需要記錄的決定就留空或刪掉，不要為了填滿而寫。
    6. tasks.md 每一步要能單獨驗證。 不要出現「實作 X」這種驗不了的步驟；純邏輯的步驟要指名它對應的測試檔。 每項寫成單行 —— Task Tracking 只取 checkbox 的第一行當步驟文字。
    7. 實作，然後到 Task Tracking 逐條勾選（讀的是 tasks.md 自己的 N.M 編號）。
    8. 收尾：openspec archive，change 從「還沒收完」清單消失。

    ⚠️ 目前 openspec 的步驟不帶錨點（用它自己的 N.M 編號當身分）， 所以這條路線的 commit 在「治理覆蓋率」上會被算成未治理。這是已知缺口，不是你做錯。

    什麼時候用 行為與已經核准過的承諾不符。PRD 不用改，是實作沒做到它說的事。

    會產生 plans/YYYY-MM-DD-bug-<id>.md 一份（走 plans/ 不走 openspec —— bug 通常沒有規格變更可寫，proposal 加 spec delta 對它是空儀式）

    1. 先重現，再讀程式。 這是硬規則。沒重現就直接看可疑的程式碼，會很有說服力地修錯地方 —— 而且修完你不會知道有沒有修好。
    2. 在這一頁建立並下載，放進 plans/。
    3. 先填「現象」與「重現步驟」。 現象寫可觀察的事實，不要寫推測的原因。「根因」那一段**空著**， 等真的重現之後再回來寫。
    4. 修，然後補一條防迴歸測試。 沒有測試的修復只證明「現在好了」，不證明「不會再壞」。
    5. Task Tracking 勾選。 步驟產生時就自帶錨點，不必再補鑄。
    6. commit 訊息帶上錨點 anc:t=XXXXXXXX（從 plan 檔的步驟複製）。 沒有它，這筆 commit 串不回計劃步驟，治理覆蓋率會算成未治理。

    ⚠️ 根因如果是「PRD 當初沒寫清楚」，那就不是 bug。 把它升級成「新功能」那條路線去改 PRD —— 當成 bug 修掉，同一個誤解會再回來一次。

    什麼時候用 對外行為完全不變：重構、升級相依、清理死碼、補文件、改測試結構。

    會產生 plans/YYYY-MM-DD-maintenance-<id>.md 一份

    1. 「不改變什麼」那一段先寫。 那不是註解，是驗收前提 —— 這條路線唯一的成功定義就是「外面看不出差別」。
    2. 盤點範圍要一次列完。 用一次 grep／glob 把所有要動的地方列出來，再開始改。 邊做邊發現的下場是改到一半才知道規模，然後停在半路。
    3. 執行變更。
    4. 確認對外行為未變 —— 既有測試全綠就是最好的證據； 測不到的部分（畫面、流程）實際操作一次。
    5. bunx tsc --noEmit 與 bun test 全綠。
    6. commit 帶錨點，同 Bug 那條。

    ⚠️ 做到一半發現「這樣改行為會變」——停下來。 那代表它其實是新功能或 bug，換一條路線重開，不要讓它在維護的名義下偷偷改掉承諾。

    三條路線共通：這一頁只產生文件，不會寫進你的專案資料夾。 下載或複製之後由你自己放回建議路徑 —— 那條界線是刻意的， 讓 App 直接寫檔等於把它變成可以在你所有專案裡任意建檔的東西。
