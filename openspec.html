    先問一句：這件事改了「對外承諾」嗎？
    
      
    改了走新功能。承諾照舊但行為對不上，走 Bug。剩下的都是維護。
    

      
    
        
        
        
      
    

      
    
        
    PRD 說的話要跟著改的時候走這條：新增能力、動到驗收條件、範圍變大或變小。
          產出四份文件，落在 openspec/changes/<id>/。
    
        
      
          
    1. 先改 PRD。承諾變了，change 才有依據可以引用。
      2. 
          
    2. 回這一頁建立，把四份檔案放回上面列出的路徑。
      3. 
          
    3. proposal.md 補上 Non-goals。openspec/config.yaml 要求這一段，
            因為範圍沒有邊界的提案會在實作途中一路長大。
      4. 
          
    4. spec.md 用 ## ADDED 或 ## MODIFIED Requirements
            標明這次是新增還是修改。
      5. 
          
    5. design.md 有技術取捨才寫，其餘留空。
      6. 
          
    6. tasks.md 每一步都要能單獨驗證，而且寫成單行。Task Tracking 只讀 checkbox 的第一行。
      7. 
          
    7. 實作，回 Task Tracking 逐條勾選。
      8. 
          
    8. openspec archive 收尾，這個 change 就從「還沒收完」消失。
      9. 
        
    
        
    openspec 的步驟用它自己的 N.M 編號當身分，身上沒有錨點，
          所以這條路線的 commit 在治理覆蓋率上會被算成未治理。這是已知缺口。
    
      
    

      
    
        
    行為跟已經核准過的承諾對不上的時候走這條。PRD 維持原樣，
          問題出在實作沒做到它說的事。產出一份 plan，落在 plans/。
    
        
      
          
    1. 先重現。在讀任何可疑的程式碼之前，讓它當著你的面壞一次。
            少了這一步，你會很有說服力地修錯地方，而且修完不知道有沒有修好。
      2. 
          
    2. 回這一頁建立，放進 plans/。
      3. 
          
    3. 填「現象」與「重現步驟」。現象寫看得到的事實，把推測留給「根因」那一段，
            等真的重現之後再回來寫。
      4. 
          
    4. 修，然後補一條防迴歸測試。只有測試能證明它不會再壞。
      5. 
          
    5. Task Tracking 勾選。步驟產生時就自帶錨點。
      6. 
          
    6. commit 訊息複製那一步的 anc:t= 錨點，這筆 commit 才串得回計劃。
      7. 
        
    
        
    根因如果落在「PRD 當初沒寫清楚」，改走新功能那條路線去修 PRD。
          當成 bug 修掉，同一個誤解過一陣子會再回來一次。
    
      
    

      
    
        
    對外行為完全不變的時候走這條：重構、升相依、清死碼、補文件、改測試結構。
          產出一份 plan，落在 plans/。
    
        
      
          
    1. 先寫「不改變什麼」。這條路線的成功定義就是外面看不出差別，
            那一段是驗收前提。
      2. 
          
    2. 一次 grep 把要動的地方列完再開始。邊做邊發現的下場是改到一半才知道規模。
      3. 
          
    3. 執行變更。
      4. 
          
    4. 既有測試全綠就是最好的證據；測不到的部分（畫面、流程）實際走一次。
      5. 
          
    5. bunx tsc --noEmit 與 bun test，然後 commit 帶錨點。
      6. 
        
    
        
    做到一半發現「這樣改行為會變」，停下來換路線。
          維護的名義底下偷偷改掉承諾，是最難追的那一種。
    
      
    

      
    三條路線共通：這一頁只產生文件，放回專案資料夾由你自己做。
        讓 App 直接寫檔，等於把它變成可以在你所有專案裡任意建檔的東西。那條界線是刻意留的。
