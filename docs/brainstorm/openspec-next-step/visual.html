適合

流程接得上，前提是分頁切的是整頁，不是只切左欄。

Wishlist 是捕捉、Changes 是推進未完成、Specs 是已生效承諾。 這三件事順序對、形狀不同，不該疊在同一份清單裡。 有未完成 change 時預設停在 Changes；Wishlist 不再蓋過 16 個坑。 跨頁用連結與徽章，不靠同時看見三份清單。

各頁放什麼 · 依 OpenSpec 順序

功能不共用一欄。哪一頁在做哪件事，就只放那件事。

上一版的「列上有下一步按鈕、卡住原因、k/N」全部留在 Changes。Wishlist 與 Specs 不再假裝自己是同一種清單。

Wishlist

捕捉還沒變成 change 的想法

  1. 專案簡寫與取號TXTML、尚未設簡寫時先設
  2. 新增類型、說明、貼截圖、存檔／取消
  3. Active勾選、編輯、撰寫 Spec、移除
  4. 送出寫 handoff，跳到 openspec.html 開新 change
  5. 封存已寫成 spec 的願望，只讀

Changes

推進還沒收完的提案

  1. 此刻該推16 個裡只亮一個建議，不鎖其他列
  2. 待實作k/N、卡住原因、開始第一步
  3. 進行中繼續下一題、複製交接、缺檔就寫缺的那份
  4. 選中展開檔案proposal / design / tasks / spec，標出 next
  5. 中欄檔案 + 卡住橫幅同一句話，可捲到下一步
  6. 右欄這個 Change進度、健康、archive 指令
  7. 已完成預設收合，含已封存

Specs

讀已生效的承諾，不是待辦佇列

  1. 說明這不是待辦archive 之後才會出現在這裡
  2. 現況規格清單開 change 改這份／對照進行中的 delta
  3. 中欄讀 spec.md橫幅重複「這份已生效」
  4. 右欄誰在改這份有 delta 就連回 Changes 那個 change

流程

三個標籤頁就是三個階段。頁面切換要接得上，不能變成斷點。

Wishlist → 送出 / 撰寫 Spec
維持現況：寫 handoff，跳 openspec.html 開新 change。精靈結束後回到工作台，停在 Changes，並選中剛建的那個。
Changes → 推下一步
待實作與進行中可以同時存在。推 B 不必先收完 A。主按鈕開對的檔、複製交接、或複製 archive 指令。Change 裡的 delta spec 在這一頁開，不必跳到 Specs。
archive 之後才進 Specs
現況規格從這裡讀。「開 change 改這份」回到開新 change 的精靈，然後再進 Changes。有進行中的 delta 時，「對照」跳回那個 change，而不是把 Specs 變成第二份佇列。

適不適合 · 四條約束

  • YES預設頁是 Changes。有未完成就不要先停在 Wishlist，否則又在加速開新坑。
  • YES標籤上一定有數字。藏起來的 16 個 change 若沒徽章，等於安靜地少列。
  • YES深連結記住分頁。?change= 開 Changes；?tab=specs 開 Specs。從 Task Tracking 進來不能落到空白的 Wishlist。
  • NO不要只把左欄切成標籤。中欄編輯器與右欄「這個 Change」是 Changes 的功能。掛在 Wishlist／Specs 上會變成死面板。

仍要做

  • Changes 列上的下一步。上一版的 k/N、卡住原因、主按鈕，原封放進 Changes 頁。
  • 卡住說明掛編輯器上方。不寫進使用者的 OpenSpec 檔。
  • 交接只複製指令。App 不跑 agent、不自動勾、不自動 archive。
  • 進行中不鎖其他列。分頁解決的是三種工作搶欄位，不是一次只能有一個坑。

仍不做

  • 不做看板。
  • 不讓 Wishlist 當首頁。有 16 個未完成時，那是在幫 C0 加速。
  • 不把 Specs 做成待實作／進行中。它沒有 tasks.md，硬分類會永遠待實作。
  • 不為了對照現況規格而強迫切頁。Changes 裡可以直接開 openspec/specs/…；Specs 頁是瀏覽用。
