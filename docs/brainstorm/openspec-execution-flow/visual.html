OpenSpec · 在執行流程裡的位置

它不是 PRD，也不是實作。它是可執行的變更信封。

Anchorline 的治理鏈是「PRD 撰寫 → 結構 gate → 簽核 → openspec change → commits → PR → release」。 OpenSpec 接在簽核之後、程式碼之前：把「我們同意做」收成一筆對現況規格的 delta， 讓 agent 可以按 tasks.md 實作，做完再 archive 併回真相。

整條產品鏈

01
PRD
產品要做成什麼。人讀的規格，在工作台-PRD。
02
Gate / 審閱
結構過了才能送簽。還沒授權開工。
03
簽核
人批准這份產品意圖。到這裡仍不是執行單位。
04 · 執行單位
OpenSpec change
一筆可實作的變更：proposal、delta spec、design、tasks。工作台-OpenSpec 管這一截。
05
Commit / PR
實作留下的 git 紀錄。Tracking 用錨點串回來。
06
Release
發布。change 早在這之前就該 archive 進現況規格。

openspec/specs/ · 真相

系統現在怎麼運作。行為契約（SHALL / MUST），不是實作計畫。archive 之後才會改這裡。工作台上的 Specs 分頁讀的就是它。

openspec/changes/ · 提案

我們想改成什麼。一筆 change 是一次執行。多筆可以同時存在、互不覆蓋真相。待實作／進行中列的就是還沒 archive 的這些資料夾。

一筆 change 怎麼走完

誰動手

步驟誰做App 做什麼
捕捉願望 人 · App Wishlist 新增／送出
開 change、寫 artifact 人 · agent propose 開新 change 精靈；工作台編檔
狀態 / 下一步是哪份檔 openspec CLI 只讀 list / status --json
勾 tasks.md 人 · Tracking 只翻一個方框字元（D10a）
apply 改程式碼 agent · 終端 不跑。只複製交接指令
archive 併回真相 人 · CLI / skill 不跑。白名單沒有 archive
讀現況規格 人 · App Specs 分頁開 openspec/specs/

所以截圖裡那 16 個檔還在，是因為執行卡在信封裡，不是卡在清單。 待實作 = artifact 在、tasks 還沒開始勾。進行中 = apply 做了一半。 Specs 會出現，是因為更早的 change 已經 archive 過——那一截已經走完，不是另一批待辦。 App 被設計成管信封、追進度、產生指令；真正改程式與改寫真相，留在 agent 與 CLI。
