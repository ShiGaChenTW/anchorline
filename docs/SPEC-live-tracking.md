# SPEC — Live Tracking（追蹤中 · live）

> 可移植規格。描述「在多個專案的多個進度文檔中，自動判定**哪一份是 agent 此刻正在動的**」這件事的設計、契約與實作。
> 參考實作：本 repo `packages/dashboard-core/src/tracking.ts`（核心 78 行）＋兩個消費端。
> 與 `docs/TRACKING-hook-contract.md` 重疊：該檔是本文的早期薄版，且路徑已過期（寫 `tui-ts/src/tracking.ts`，實際已搬到 `packages/dashboard-core/`）。以本文為準。

## 1. 問題

Agent 在跑的時候，人不在終端前面。回來時第一個問題永遠是「它現在在做什麼？」

Dashboard 有一堆專案、每個專案有一堆 plan 文檔。要回答那個問題，使用者得自己想「剛剛我叫它做哪個專案」然後手動翻到那一份。**判斷成本落在人身上，但機器明明有足夠資訊自己判斷。**

要解的就是這一件事：讓 dashboard 自己指出「這一份，就是現在正在動的」。

## 2. 核心概念 — 兩個獨立的「當前」

移植時**最容易搞混、也最該先釘死**的一點：

| 概念 | 誰決定 | 生命週期 | UI 表現 |
|---|---|---|---|
| **selection（選取）** | 使用者按鍵盤／點滑鼠 | 使用者不動就不變 | 反白列 |
| **tracking target（追蹤目標）** | 系統自動判定 | 隨檔案活動持續變 | 灰色 `•` 圓點 |

**追蹤中 ≠ 已選取。** 兩者可以指向不同檔案，而且經常如此——使用者正在看 A 的內容，agent 在寫 B，`•` 就該出現在 B 上。任何把兩者合併成單一 state 的實作都是錯的。

## 3. 判定演算法

兩段式，優先序由上而下。**第二段是主力，第一段是精準化選配。**

```
trackingTarget(watchedFiles: Path[], signalPath: Path, now: Timestamp) -> Path | null

  # 段 1 — 明確訊號（精準，需外部寫入）
  if signalPath 存在:
      if now - mtime(signalPath) <= FRESHNESS_WINDOW:      # 預設 30 分鐘
          raw = 第一行(讀取(signalPath)).trim()
          if raw 非空 且 raw 存在於檔案系統:
              if raw 是檔案 且 副檔名是 .md:  return raw
              if raw 是目錄:
                  plansDir = raw 以 "plans" 結尾 ? raw : raw/plans
                  return plansDir 內 mtime 最新的 .md      # 可能為 null

  # 段 2 — 自動跟隨（零設定，永遠可用）
  return watchedFiles 中 mtime 最新者                       # 空清單則 null
```

三個不可省略的性質：

- **全程 fail-soft。** 任一步失敗（檔不存在、讀取錯誤、路徑失效、權限問題）都不是錯誤，是「退回段 2」。整個函式不該有任何 throw 路徑。
- **`now` 必須可注入**，否則新鮮度邏輯無法測試。
- **純函式。** 不讀全域設定、不碰 UI state。監看清單與訊號檔路徑都由呼叫端注入。這是它能被 TUI 與 web 兩個完全不同的前端共用的唯一原因。

### 為什麼是 mtime 而不是別的

考慮過也捨棄的方案：

- **進程偵測**（找正在跑的 agent process）— 跨平台地獄，而且 agent 跑在哪跟它寫哪個檔沒有必然關係。
- **要求 agent 主動註冊** — 沒註冊就完全不能用，違反「零設定可用」。
- **inotify/FSEvents 事件流當唯一真相** — 啟動瞬間沒有事件，冷啟動就是空的。

mtime 的好處是**它已經在那裡了**。agent 寫檔是它本來就會做的事，不需要它配合任何協定。段 2 因此是「零設定、零侵入、冷啟動即正確」。

段 1 存在的唯一理由是**多專案同時活動時的消歧**：兩個 agent 在兩個專案各寫各的，mtime 只能指出「最後一個寫的」，訊號檔才能指出「使用者此刻關心的那個」。

## 4. 訊號檔契約

移植時這是唯一的跨進程介面。

| 項目 | 規格 |
|---|---|
| 路徑 | `$XDG_CONFIG_HOME/<app>/active`（本實作：`~/.config/agenttask-tui/active`） |
| 格式 | **純文字，取第一行**。多餘行忽略，尾端換行可有可無 |
| 內容 | 絕對路徑之一：① `.md` plan 檔 ② 專案根目錄 ③ `plans/` 目錄 |
| 新鮮度 | 由**檔案 mtime** 決定，不寫時間戳在內容裡。超過 30 分鐘視為過期 |
| 寫入方式 | **必須原子**：寫 tmp → `rename()` 同檔系覆蓋 |
| 寫入者 | 外部（agent hook、CLI wrapper、editor 外掛…）。消費端從不寫 |

**為什麼新鮮度用 mtime 而非內容裡的時間戳**：寫入者只要 `echo path > active` 就完成契約，不需要懂時間格式、不需要處理時區。降低寫入端門檻直接決定這個機制會不會被接。

**為什麼必須原子寫**：消費端在 render loop 裡以最高每秒一次的頻率讀這個檔。非原子寫會讓它讀到半行路徑，然後存在性檢查失敗、悄悄退回段 2——症狀是「訊號有時候有用有時候沒用」，極難除錯。

**為什麼要有 30 分鐘過期**：這是整個設計最重要的一個防呆。訊號檔是外部寫的，寫入者隨時可能停止運作（升級、被停用、崩潰），但檔案會留在磁碟上**永遠指向一個過時的目標**。沒有過期機制的話，一個死掉的 hook 會讓 dashboard 永遠指錯地方，而且看起來完全正常。

> 本 repo 的真實案例：訊號寫入者（`skill/agenttask-tui/scripts/launch_tui.ts`）於 2026-07-31 因多視窗守衛失效被停用，殘留的 `active` 檔在磁碟上躺了一週，內容指向一個無意義路徑。因為有 30 分鐘過期，dashboard 從第 31 分鐘起就自動退回段 2，**使用者完全無感**。這個設計決策的價值在寫入端死掉的當下才兌現。

## 5. 消費端表面

同一個 `trackingTarget()` 回傳值驅動三個 UI，移植時按需取用：

| 表面 | 說明 | 本實作位置 |
|---|---|---|
| **追蹤圓點** | 側欄清單中，追蹤目標那一列尾端加灰色 `•` | `tui-ts/src/render.ts:339,444` ／ `gui-web/src/client.ts:274` |
| **live 面板** | 專用視圖：只顯示追蹤目標，含專案名／進度／步驟清單／執行中 agent | `tui-ts/src/render.ts:1151`，標題 `追蹤中 · live` |
| **model 欄位** | 序列化模型上的 `tracking: string \| null` ＋ 每個 plan 的 `isTracking: boolean` | `gui-web/src/model.ts:33,90` |

**live 面板不自動彈出。** 它是 view mode 之一（`full → simple → tracking` 循環，按 `m`），使用者手動切換並持久化到 config。理由：自動切換視圖會在使用者正在讀別的東西時把畫面搶走——那比「沒看到進度」更糟。**判定是自動的，呈現是手動的。**

**空狀態不暴露判定細節。** 沒有追蹤目標時顯示「等待 agent 開始執行…」，不顯示「訊號檔過期，已退回 mtime fallback」。內部機制對使用者無意義。

## 6.「live」的定義 — 更新節奏

live 不是輪詢單一數字，是兩層混合：

- **事件驅動**：`watch()` 監看每個 `plans/` 目錄（非遞迴），檔案變動立即重繪。
- **週期刷新**：`setInterval` 1000ms（動畫期間 125ms）。負責 mtime 重新比較、時鐘、git 狀態、agent 經過時間。

**畫面去重是必要的**：週期刷新每秒觸發，但無變化時不得重畫，否則終端閃爍且吃 CPU。實作上比對上一幀輸出字串，相同就跳過。

`trackingTarget()` 在**每次重繪時重新呼叫**，不快取。它是純函式且只做幾個 `stat`，成本遠低於一次終端重繪；快取只會製造「追蹤點卡住不動」這類 bug。

## 7. 移植檢查表

要參數化的（不要硬編碼）：

- [ ] 訊號檔路徑 — 隨 app 名稱變，且必須可注入（測試要能指到隔離沙箱，**絕不可碰使用者真實檔案**）
- [ ] `FRESHNESS_WINDOW` — 30 分鐘是本場景的值。互動更頻繁的場景可縮短
- [ ] 「plan 檔」的判準 — 本實作是 `.md`。換成其他格式時，段 1 的副檔名檢查與段 2 的目錄掃描要同步改
- [ ] 目錄約定名 `plans` — 段 1 的目錄分支依賴它

可直接照搬的：

- [ ] 兩段式優先序與 fail-soft 語意
- [ ] 原子寫（tmp + rename）
- [ ] selection ／ tracking 分離
- [ ] 每次重繪重算、不快取

**移植時最容易漏掉的**：把 `trackingTarget()` 抽成純函式，卻讓消費端各自寫「怎麼用」。本 repo 在 vocab、keymap、markdown 上各犯過一次同樣的病——值抽走了、用法留在各消費端，隔天就漂移。判別式：**第二個消費端還寫不寫得出這段邏輯？寫得出來就不是單一真相，只是多了一張參考表。**

## 8. 測試規格

核心函式的必要案例。`trackingTarget()` 的簽章已為此設計好——`nowMs` 與 `signalPath` 都可注入，不需要碰系統時鐘或真實家目錄。

> ⚠️ **本 repo 目前對這個函式有 0 個測試。** 簽章是可測的，但沒人寫。移植時請把下表當成待補清單，不是既有成果。

| # | 情境 | 期望 |
|---|---|---|
| 1 | 訊號檔不存在 | 退回 mtime 最新 |
| 2 | 訊號新鮮 ＋ 指向存在的 `.md` | 回傳該檔 |
| 3 | 訊號新鮮 ＋ 指向專案根目錄 | 回傳該專案 `plans/` 內最新 `.md` |
| 4 | 訊號新鮮 ＋ 指向 `plans/` 目錄 | 同上，不重複附加 `plans` |
| 5 | 訊號 mtime 超過 30 分鐘 | **忽略訊號**，退回 mtime 最新 |
| 6 | 訊號新鮮但路徑已不存在 | 退回 mtime 最新 |
| 7 | 訊號檔內容為空／全空白 | 退回 mtime 最新 |
| 8 | 訊號指向的目錄內無 `.md` | 退回 mtime 最新 ※ |
| 9 | 訊號指向存在但非 `.md` 的檔案 | 退回 mtime 最新 |
| 10 | 監看清單為空且無有效訊號 | 回傳 null |
| 11 | 監看清單含已刪除的檔 | 跳過該檔，不影響其他 |

※ 案例 8/9 的機制值得看清楚：段 1 的所有失敗路徑（含「目錄解析成功但裡面是空的」）都統一回傳 `null`，而 `trackingTarget` 用 `if (sig) return sig` 判斷——**`null` 是 falsy，所以一律穿透到段 2**。這代表段 1 沒有「我決定是 null」這個表達能力，它只能說「我有答案」或「我沒答案」。

移植時這是個要意識到的選擇：若你需要「訊號明確指向一個空專案 ⇒ 就顯示空，別跳去別的專案」，得把 `readSignal` 的回傳型別從 `Path | null` 改成三態（`found` / `no-signal` / `signal-but-empty`），否則做不到。現行雙態設計的好處是簡單且永遠有輸出，代價就是這個表達力缺口。

**測試紀律**：所有涉及訊號檔的測試一律寫到臨時隔離路徑。本 repo 的 `skill/agenttask-tui/scripts/launch_tui.test.ts:6` 有明文警告，因為真實檔案被測試汙染過。

## 9. 寫入端範例

最小契約實作（Claude Code hook，每個 turn 寫入當前專案）：

```json
{
  "hooks": {
    "UserPromptSubmit": [{
      "hooks": [{
        "type": "command",
        "command": "d=~/.config/<app>; mkdir -p $d; printf '%s\\n' \"${CLAUDE_PROJECT_DIR:-$PWD}\" > $d/.active.tmp$$ && mv $d/.active.tmp$$ $d/active"
      }]
    }]
  }
}
```

要精準到單一 plan 檔，就在建檔流程末端寫該 `.md` 的絕對路徑而非專案根目錄。

任何能執行一行 shell 的東西都能當寫入者——這是刻意的。**契約越窄，接得上的東西越多。**
