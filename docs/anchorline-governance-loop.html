AI-Native SDLC Playbook · 05 對照 Anchorline

治理鏈為什麼還是一條線

Anchorline 已經在做的事，跟 playbook 講的是同一件事的不同一半：playbook 講「怎麼讓 agent 跑完整條 SDLC」，Anchorline 講「怎麼證明這些 agent 做過的事被治理過」。把兩邊疊起來，缺口出現在鏈的兩端——不是中間。

圖

Anchorline 治理鏈迴圈

七站順時針，每一站都寫回同一組錨點。實線是今天已經在跑的環節；鏽紅虛線那兩段不存在——所以它現在是一條線，不是迴圈。

圖 A 治理鏈七站 · 錨點為共用狀態
Loop · 7 stations · 1 hub

Anchorline 有一處比 playbook 更嚴。原文在 R1 的治理段寫的是「寫程式的那個 agent 沒有任何途徑核准它」——那是人／agent 粒度的職責分離。Anchorline 的 authorAgentFamily 把粒度再降一層：同一個 agent 族系撰寫的文件，不能由同族系核准。GitHub 的 CODEOWNERS 與分支保護只認人不認族系，抓不到這一類。

現況依 README.md 與 docs/PRD.md 判讀，未逐一核對原始碼；建議是判斷，不是原文的主張。真的要動工前，每一站都該回去驗一次。

情境 A

每一站什麼時候會走到

跟著圖順時針讀。每一站回答四件事：什麼時候會走到這裡、實務上長什麼樣、誰在操作、現在卡在哪。

P1

意圖 intent/

什麼時候走到這裡
有人覺得「這件事該做」，但還沒到能寫成 PRD 的程度。
實務上長什麼樣
一則 Slack 訊息、一次 UAT 失敗後的抱怨、一個客訴。今天它們沒有家，被口頭轉成 PRD。
誰在操作
提出者本人，通常不是工程師。這是唯一一站不需要懂規格格式的入口。
現在卡在哪
治理鏈從 PRD 起手，等於默認「已經有人把想法寫成規格了」——而那是傳統 SDLC 最慢的一段。想法本身不在稽核軌跡上。
D1

規格 PRD

什麼時候走到這裡
意圖確定要做，開始把它寫成能被審的東西。
實務上長什麼樣
Anchorline 編輯台：引導撰寫 ＋ 結構 gate ＋ Markdown 即時預覽。
誰在操作
人下指令、agent 起草，gate 判定結構是否完整。
現在卡在哪
結構 gate 檢查的是「章節齊不齊」，playbook 要的是政策約束。而且沒有記錄「這份 PRD 是在哪一版 skill／政策下寫的」——這一欄沒有，spec 的可稽核性就不完整。
B1

計畫 plans/

什麼時候走到這裡
規格過了 gate，要拆成可執行的步驟與檔案清單。
實務上長什麼樣
Task Tracking 直接讀 plans/*.md，checkbox 可勾，右欄三層稽核軌跡。plans/ 本來就是 plan.md 的家。
誰在操作
plan mode 產出、人核准；勾選由執行中的 agent 或人同步。
現在卡在哪
缺對照：merge 的 diff 有沒有還吻合 plan？「plan.md 未同步」應該是治理鏈上的一種違規標記，跟 authorAgentFamily 走同一套 replay。
R2

核准 簽核閘

什麼時候走到這裡
東西要往下一步推之前的人為關卡。
實務上長什麼樣
審閱／簽核畫面：gate 未過就擋核准，治理鏈 replay 會標出違規。這是全鏈做得最好的一段，概念上等同 playbook 的 ask-hook。
誰在操作
人。而且必須是人——這一站的價值就在於它不能被 agent 代掉。
可以再補
「封鎖必須自己解釋自己」：擋下時同時顯示理由與取得核准的途徑，而不只是把按鈕變灰。
R1

實作 commits / PR

什麼時候走到這裡
核准過了，agent 開始寫，產出 commits 與 PR。
實務上長什麼樣
跨 repo PR 雷達；authorAgentFamily 擋掉同族系自審——這一條比原文更嚴。
誰在操作
agent 寫、人審。多線同時在飛的時候，這一站是瓶頸所在。
現在卡在哪
缺 REVIEW.md 那一層（審查政策、Important／Nit 的界線、要跳過什麼），而且審查發現本身沒進軌跡——它是 playbook 明列的六份產物之一。
R3

發布 release

什麼時候走到這裡
PR 併進去了，要發版。
實務上長什麼樣
發布頁追蹤 release，鏈的末端是 commits → PR → release。
誰在操作
CI 觸發、人確認。
現在卡在哪
缺 rollback。原文說 rollback 應該是整條 pipeline 中被演練得最熟的路徑，因為 M1 的 3σ 會呼叫它。鏈目前只有單向，走不回來。
M1

訊號回寫

什麼時候走到這裡
發布之後，或任何一關失敗的當下。
實務上長什麼樣
UAT 失敗、gate 未過、PR 失敗、release 異常——四種訊號目前全部停在畫面上等人看。
誰在操作
應該是系統自己。需要人記得回頭看的迴圈，等於沒有迴圈。
現在卡在哪
四種訊號都已經有錨點，只差最後一步：自動生成一份帶錨點的 intent.md 草稿丟回 P1。做到這裡，Anchorline 才從「看板」變成「迴圈」。
HUB

錨點 · 稽核軌跡

它不是一站
是累積狀態。七站都寫回同一組錨點，這才是 Anchorline 真正在賣的東西。
現在卡在哪
操縱 agent 的設定沒有被治理。CLAUDE.md、.claude/skills/、.claude/settings.json 決定了 agent 的行為，但它們的變更不在軌跡上——治理了產出，沒治理產出者的設定。
情境 B

這張圖什麼場合拿出來用

上一節是圖裡面；這一節是圖外面——什麼決策該把它攤開，什麼問題不該問它。

四個該用的場合

  1. 排優先序的時候。兩段鏽紅就是排序的答案：P1 最便宜（一個目錄 ＋ 一份範本），M1 最有價值（訊號已有錨點，只差自動生成草稿）。中間五站全是「加強」，不是「開路」——可以排隊。
  2. 對外解釋定位的時候。被問「Anchorline 到底是什麼」，這張圖一句話回答：它記錄鏈，不執行鏈。B4 那條刻意不自己做 hook runtime 的判斷，理由就在這張圖上——中心是狀態，不是執行器。
  3. 收到功能請求的時候。先問「它落在哪一站」。落在中間五站是改良，可以排；落在兩段鏽紅是補結構，會改變產品敘事。這個分類比「重要／不重要」有用得多。
  4. 解釋為什麼 R2 是護城河的時候。核准閘是全鏈唯一「已具備」的一站，而 authorAgentFamily 的族系粒度是 GitHub 原生機制抓不到的。要講差異化，指這一站。

兩個不該用它的地方

  • 不要拿它談 M2/M3（掃描與 on-call）。對單人＋多 agent 的情境優先度最低，且高度依賴 Claude Enterprise。硬塞進圖裡會讓兩個真正的缺口失焦——但入口要先留好，那個入口跟 M1 是同一個。
  • 不要拿它當實作依據。現況欄依 README 與 PRD 判讀，未逐一核對原始碼。這張圖適合排序與對外說明，動工前每一站要回去驗。
延伸

上下文維度

這一節不在 playbook 裡，也不在 14 條 Play 裡。它是把「上下文管理」疊到這張圖上之後才長出來的兩件事——一件讓表縮短，一件讓表變長。

一、錨點少了一個欄位

現在每個錨點記錄「產出了什麼」，沒記錄「產出者當時看得到什麼」。同一份 PRD，在不同的 CLAUDE.md、不同 skill 版本、不同模型下跑，產出不一樣。治理鏈把產物釘死了，把產物的生成條件放生了。

這不是 B2 那條「把 CLAUDE.md 納入監看」。監看給的是 changelog，上下文出處給的是 lockfile：

changelog（B2 給的） CLAUDE.md 在 9/1 變過
lockfile（上下文出處給的） 這個 PR 由 CLAUDE.md@a3f2 ＋ skills[x@2, y@1] ＋ plan.md@rev4 ＋ model=opus-5 產出

前者讓你查，後者讓你重播。差別在能不能回答「它為什麼會那樣做」與「換一次它還會不會那樣做」。

四列塌成一件事

一旦這樣看，表裡四列不是四個功能，是同一個機制的四個切面：

原本的列它其實在要的東西
D1 需求與設計合併記錄「PRD 寫作當時生效的 skill 版本」
B1 Plan modeplan 與 diff 是否還吻合——plan 本身就是 context 的一部分
B2 CLAUDE.mdCLAUDE.md／skills／settings 進軌跡
B3 Skills 作為機構知識「這份 PRD 是在哪一版政策下寫的」

B3 那句話是原文自己寫的。它就是上下文出處，只是沒被命名——所以它被切成四塊散在表裡，看起來像四個中等優先的改良，實際上是一件事。

四類上下文，各自缺在哪

上下文類別具體是什麼現在在哪進得了軌跡嗎
doctrineCLAUDE.md、專案內規則git，但 App 不知道它存在否
政策 / skills.claude/skills/、掛載中的政策檔案系統否
planplans/*.mdAnchorline 已經在讀讀得到，沒版本綁定
執行者模型、agent 族系、worktreeauthorAgentFamily 已進鏈四分之一已具備

最後一列是關鍵：Anchorline 已經做了這件事的四分之一，只是沒意識到。authorAgentFamily 不是一條孤立的職責分離規則——它是「把執行者的身分綁進錨點」，也就是上下文出處的第一個欄位。剩下三類是同一個欄位往外長。

前置依賴：這件事不是免費的。要拿到「當時哪些 skill 生效」，資料只有一個來源——hook log 或 OpenTelemetry。B4 建議的那半（讀 log、把 allow／block／ask 畫進鏈）不是一個獨立的低優先功能，是這件事的進料管。原文把 B4 判成優先度最低，那個判斷在加入上下文維度之後要翻過來。

二、表上沒有的第 15 格

B5 原文問的是「一個人審查得過來幾條線」。從上下文角度看，瓶頸不是審查吞吐量，是每條 session 有自己的 context window，彼此看不見。

兩個 agent 在兩個 worktree 上，可以做出互相矛盾的決定，而且各自都會通過自己那關的 gate——因為 gate 檢查的是這條線的內部一致性，不是跨線的一致性。PR 雷達看得到兩個 PR，看不到兩者衝突。

playbook 沒有這條，14 條 Play 也沒有這條。它只有在把上下文當成一等公民之後才會出現。

為什麼是 Anchorline 該做

偵測跨 session 矛盾，需要同時握著兩條線的錨點。CI 沒有，GitHub 沒有，agent 自己更沒有——它的 context window 裡看不到另一條線。Anchorline 有，而且是唯一有的。

最小可行版

  • 兩份在途的 plan 碰到同一個錨點 → 標記。不需要理解語意，只需要算交集。這是今天就寫得出來的東西。
  • 升一級：同一檔案在兩條線上都被列為「要改」，但兩份 plan 的敘述不一致 → 升為違規，走 authorAgentFamily 同一套 replay。
  • 目前的解法是在 PROJECTS.md 手寫一段「跨 session 接縫」——人工的上下文同步，不進軌跡，靠記得。這正是它該被機器接手的訊號。

對這張圖的影響：不改

上下文出處是第二個累積狀態，而迴圈圖只能有一個中心——兩個中心就是兩張圖。它不是第八站，是中心的第二個欄位：現在存「產出了什麼」，該存「產出了什麼 × 產出者看得到什麼」。真要畫，是另一張矩陣圖，不是往這張塞。

對照

14 條 Play 的判定

圖只畫了七站；playbook 的 14 條 Play 逐條判定在這裡。缺口 5、部分 8、已具備 1。掛上下文出處的四列不是四個功能，是同一個機制的四個切面。

PlayAnchorline 現況判定改版建議
P1 捕捉 intent.md治理鏈從 PRD 撰寫起手。沒有更早、更粗、非工程師可寫的入口。缺口在編輯台前面加一層 intent/：欄位極少的 proto-spec（問題／預期成果／受影響系統／限制／開放問題），一建立就配錨點。PRD 變成 intent 的下游。
D1 需求與設計合併上下文出處編輯台已有 PRD 引導撰寫 ＋ 結構 gate ＋ Markdown 即時預覽。部分把品牌／安全／合規／UX 政策做成可掛載的 skill 清單，並在 PRD 上記錄「當時生效的 skill 版本」。
B1 Plan mode / plan.md上下文出處Task Tracking 讀 plans/*.md，checkbox 可勾、右欄三層稽核軌跡。部分缺對照：merge 的 diff 是否還吻合 plan？把「plan.md 未同步」做成治理鏈上的違規標記。
B2 CLAUDE.md上下文出處repo 有 CLAUDE.md，但它不是 Anchorline 的治理對象——App 不知道它存在。缺口把 CLAUDE.md、.claude/skills/、.claude/settings.json 納入監看清單。操縱 agent 的設定本身就該是被治理的產物。
B3 Skills 作為機構知識上下文出處Agents 頁已有 agent 角色、prompt、進場作業。部分從「agent 名冊」擴成「policy → skill → 負責人」登錄表：每條政策一位負責人、一份真相來源、一個 skill 版本。
B4 Hooks 建置護欄無。Anchorline 不介入 agent 的執行期。缺口不建議自己做 hook runtime。但可以把 hook 決定收進稽核軌跡：讀 OpenTelemetry 或 hook log，把 allow／block／ask 畫在鏈上。

B5 平行 session 與 subagentAgents 頁 ＋ 跨 repo PR 雷達已接近「多線在飛」的視圖。部分PR 雷達再往前一步：顯示還沒變成 PR 的在途 worktree／session。「一個人審查得過來幾條線」目前沒有畫面在回答。
＋ 表上沒有的：跨 session 矛盾偵測——兩條線各自過 gate，卻互相衝突。
T1 回饋迴圈UAT 是人眼迴圈：逐題勾選，失敗與不測必填說明，結果寫回同一份 markdown。部分缺機器迴圈的證據：make test 輸出、build log、截圖差異目前不進治理鏈。收進來，「證據來自工具鏈」才成立。
T2 持續 evals無。缺口全套 eval 太重。最小可行版：UAT 失敗題與事故各留一則案例，在 CLAUDE.md 或 skills 變更時提醒重跑。
R1 PR 審查迴圈跨 repo PR 雷達已有；authorAgentFamily 的職責分離比原文更嚴。部分缺 REVIEW.md 這一層，且審查發現本身沒進軌跡——它是 playbook 明列的六份產物之一。
R2 Hooks 核准閘審閱／簽核畫面：gate 未過擋核准；replay 會標出違規。已具備概念上就是 playbook 的 ask-hook。可補「封鎖必須自己解釋自己」：擋下時顯示理由與取得核准的途徑。
R3 CI/CD 與部署發布頁追蹤 release；鏈的末端是 commits → PR → release。部分缺 rollback。原文說它應該是整條 pipeline 中被演練得最熟的路徑。補一個 rollback 事件型別，鏈才走得回來。
M1 閉環無。UAT 失敗、gate 未過、PR 失敗都停在畫面上等人看。缺口最大的一塊，也最像 Anchorline 該做的事。讓訊號自動生成帶錨點的 intent.md 草稿丟回 P1。做到這裡，才從「看板」變成「迴圈」。
M2/M3 掃描與 on-call無。缺口對單人情境優先度最低，且高度依賴 Claude Enterprise。先不做，但把「發現 → intent.md」的入口先留好——跟 M1 是同一個。

三個結構性判斷

  1. 鏈少了最前面一段。playbook 的鏈是 intent → spec → plan → diff → PR → incident；Anchorline 的是 PRD → gate → 簽核 → openspec → commits → PR → release。從 PRD 起手，等於默認「已經有人把想法寫成規格了」。補上 intent 層是投報率最高的一步，也最便宜。
  2. 迴圈沒有閉合，所以它現在是一條線。四種訊號都已經有錨點，缺的只是「自動寫回一份意圖」。這一步做完，README 上那句「一條治理鏈」才會真的變成迴圈。
  3. 操縱 agent 的設定本身沒有被治理。對一個主打「證明 agent 做的事被治理過」的產品來說，這是定位上的漏洞而不只是功能缺口。
