# PRD 產品需求文件範本

> 出處：Tom Liou（湯六）〈【SOP不藏私】系列＃EP1「連猴子也會的PRD指南」〉，AAPD — As A Product Designer，2019-09-02
> https://medium.com/as-a-product-designer/sop-ep01-prd-3c6d33880c34
>
> 這份範本把該文第四章的七段結構轉成可直接填寫的骨架。原文的立場要先講清楚，否則這份範本會被誤用：
> **PRD 沒有固定格式。** 章節可依專案規模、個人習慣、迭代大小增刪，能讓開發團隊有脈絡地把產品做好就是好 PRD。
> 適用對象是小團隊裡 UIUX 兼 PM 的角色；它刻意不談需求優先級的評量方法，也不談 UX 原則與指標制定方法論。
>
> 三份文件的分工（原文第三章）：**BRD** 決定「值不值得做」，**MRD** 決定「要做出什麼差異」，**PRD** 決定「這個產品要做成什麼樣子」。
> 實務上 MRD 與 PRD 常揉成一份提案簡報，不必為了切乾淨而切。
>
> 使用方式：整份複製後逐節填寫，刪掉用不到的章節。標題採 `## N. 標題` 編號格式，可直接匯入 Anchorline 的「整份 PRD 範本」。

## 2. 產品簡介與功能

### 2.1 產品簡介（Overview）

一段話說明這個產品是什麼、解決誰的什麼問題。

### 2.2 產品價值（Value）

做這件事的理由。與產品簡介的差別在於：價值要包含**用戶定位**與**商業目標**，不只是功能描述。

### 2.3 目標客群（Target User）

主要客群 / 次要客群，各自的情境與痛點。

### 2.4 用戶故事（User Story）

> 身為 **[角色]**，我想要 **[做某件事]**，以便 **[達成某個目的]**。

## 3. 產品架構與流程

### 3.1 功能心智圖（Function Map）

產品功能模塊的集合。顆粒度取決於「RD 需要了解到多細」，以及未來路線圖要放多遠。

例：`會員資料` 模塊下掛 `編輯會員資料`／`上傳會員頭像`／`註銷會員帳號`。

檢查法：拿 **CRUD**（Create／Read／Update／Delete）逐一比對每個 Feature，看資料運算有沒有漏掉的一角。

工具不拘（Xmind、Miro、draw.io），能讓所有人看懂「現在做什麼」與「未來做什麼」就行。

### 3.2 資料結構圖（IA）

## 5. 產品指標（Metrics）

每個功能釋出前先想清楚它要達成的商業目標，再依 **Goal → Signal → Metric**（樹幹 → 樹枝 → 樹葉）往下拆，最後與 RD 談事件埋點。

| 功能 | Goal（商業目標） | Signal（觀察得到的行為） | Metric（可量測數字） | 埋點事件 |
|---|---|---|---|---|
| | | | | |

**商務指標與體驗指標的側重會隨產品屬性改變。** 有些東西埋再多事件也量不出來——例如改文案要降低的是認知負荷，那要靠 NASA-TLX、QUIS 這類量表的認知構面在發版前做質性測試。

也要反覆自問：任務完成速度變快了，用戶就會更愛用、更願意久留嗎？指標的重要程度由產品屬性決定，不是抄來的。
