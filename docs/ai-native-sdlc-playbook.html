00

程式碼不再是瓶頸

傳統 SDLC 是為了「寫程式最貴、最慢」的年代設計的。PRD、估點儀式、產品安全審查，全都是為了在那段可能長達數月的開發期之前先把方向對齊。當開發期塌縮成幾小時，這套控制就對不上現實了。

原文開宗明義：組織已經在用 AI 以一年前無法想像的速度產出程式碼，但圍繞著程式碼的流程沒有跟著變。同一批核准關卡、審查、交接與政策還在，於是 agentic coding 帶來的產能被卡在原地。

當開發階段跑得比傳統 SDLC 允許的還快，會有三件事同時成立：

  1. 瓶頸移到開發階段的左右兩側。主要是計畫、審查／測試、部署——這些階段仍然以人的速度在跑。
  2. 控制手段開始對不上現實，變得不可行。逐行手動審查在「程式是人寫的」時代說得通；一旦 agent 寫掉大部分 diff，它就跟不上了。
  3. 治理成本上升。因為例外案件仍然要走每週或每月才開一次的會議與委員會。

安全團隊的編制是照人的產出量抓的。當 agent 把程式碼產出乘上好幾倍，結果只有兩種：審查佇列愈積愈長，或程式碼在審查不足的狀態下上線。受監理的組織兩種都不能接受——所以它的安全與政策檢查必須跟上 agent 的速度。

01

什麼是 AI-native SDLC

它不是把 AI 塞進既有流程，而是把控制目標保留、把執行方式換掉：線性流程變成迴圈，AI 嵌在每一個點上，而階段之間的交接由「提交一份可被讀取的產物」自動觸發下一段。

原文提醒：這個轉變也被叫做 agentic SDLC、AI SDLC 或 agentic software development——名字不同，講的是同一件事。

貫穿整條右欄的那條線是被提交的產物（committed artifact）。每個階段以「寫一份東西進版本控制」作結，下一個階段以「讀它」開始。前段用 .md，因為產品負責人與 agent 可以讀同一份檔案；從 Build 開始，產物變成程式碼與它的紀錄。而這串 commit 本身就是稽核軌跡：誰要求了什麼、agent 產出了什麼、誰核准了。

階段 01

Plan — 計畫

想法不再排隊等人幫它寫成文件。意圖只被捕捉一次，用提出者自己的話，寫成下一階段就能直接動作的版本控制產物。

P1 捕捉為 intent.md想法、工單、告警三種入口，同一份格式 展開

intent.md 是整個開發流程的起點，它可以從三個路徑進來：有人有了想法、工單被開出來、或事故經由告警浮現（見階段 6）。

當一個人有想法時，他跟 Claude 腦力激盪，產出一份 markdown 的 proto-spec。在傳統 SDLC 裡，這個人接下來必須說服產品團隊的某人陪他寫、或替他寫。而這份 proto-spec 人讀得懂、被版本控制、下一階段可以直接消費——存成 intent.md 就結束了。

不論意圖來自事件觸發還是 agent，步驟都一樣：產品負責人在提交前審閱並修正 agent 寫的 intent.md。

傳統
一個想法要先穿過待辦項目、user story、故事點與 refinement 會議，才有人能動作。每一次交接所有權都轉移一次，所以真正到工程手上的東西，跟提出者原本的意思已經隔了好幾層。
AI-native
提出者跟 Claude 腦力激盪，把結果寫成 intent.md——一份用他自己語彙寫的 proto-spec。這份產物包含：要什麼、為什麼、在哪些限制下。重複性的流程用 skills 編碼起來。
前置
無。
基礎建設
讓非工程師也能用 Claude（claude.ai 或 Cowork）；一份講好的 intent.md 範本；一個產品負責人會盯的共享版控家。單一產品最簡單的家就是產品 repo 裡的 intent/ 資料夾。
誰來架
平台或工程團隊的一次性工作。需要一位技術成員把 intent 的家立起來、決定誰能寫入——因為貢獻者會來自整個組織。

把產物鏈放在它衍生出來的程式碼旁邊，是這個配置的重點。只有當意圖橫跨多個 repository 時，獨立的 intent repo 才值得那個額外成本；在 monorepo 裡它就是一個目錄。repo 建好之後，沒有 git 經驗的貢獻者不需要直接碰 git——一個到版本控制系統（例如 GitHub）的 connector，就能讓 Claude 從 claude.ai 或 Cowork 代為提交 markdown。

怎麼執行

  1. 提出者用自己的話跟 Claude 描述問題：今天做不到什麼、誰受影響、更好長什麼樣、什麼不在範圍內。不需要任何正式語言。
  2. 一直激盪到想法夠具體。Claude 會問分析師會問的問題：範圍、使用者、限制、成功的樣子。
  3. 請 Claude 用組織的範本寫成 intent.md。範本本身可以編成一個 skill，由技術成員建立、由主管簽核，涵蓋問題、預期成果、受影響的使用者與系統、限制、開放問題。
  4. 提出者修正 Claude 誤解的地方。
  5. 提交 intent.md 到共享的家。作者與時間戳記加入紀錄，產品負責人從這裡接手。
intent.md
# Intent: claims status self-service
Author: J. Ortiz (claims operations). Status: draft.

## Problem
Customers phone the contact center to ask where their claim is.
Handlers spend roughly a third of call time on status-only queries.

## Proposed outcome
Customers see claim status, next step and expected date in the portal.

## Affected users and systems
Claims handlers, portal team, claims-core API.

## Constraints
No new PII in the portal session. Existing authentication only.

## Open questions
Do third-party loss adjusters need access too?
治理
證據就是被提交的 intent.md：作者、時間戳記、完整修訂歷史，全部落在 intent 家的 git 歷史裡。產品負責人核准，而「送進階段 2 或退回」這個決定，被記錄成該筆 merge 或那次結案的 review。
領先指標
從第一次對話到 intent.md 被提交的時間，直接讀 intent 家的 git 歷史（含作者與時間戳）。預期是從數週的訪談與精煉週期，降到數小時。
落後指標
存活率——產品負責人接受進入階段 2 的 intent.md 佔比（相對於被關掉的）。另外還有：同一個變更的第一份 spec.md 提交之後，intent.md 又被改了幾次。
階段 02

Design — 設計

需求與設計塌縮成一次 session。政策在規格被寫下的當下就套用，而不是幾週後在審查裡才被發現。

D1 需求與設計合併產品負責人審規格，但不寫規格 展開

產品負責人核准後，Claude 拿被接受的 intent.md 產出一份需求與設計規格，過程由組織在品牌、安全、合規、UX 上的 skills 引導。產品負責人審閱這份規格，但不寫它。目標是產出一份工程團隊可以據以規劃的規格，並且把疑慮之處標記出來。

前端工作是最清楚的例子：intent.md 一被接受，產品負責人就在 Claude Design（beta）裡從 intent.md 做出 mock、迭代它，然後匯出到 Claude Code 去建。

傳統
需求與設計是兩個由不同團隊跑的階段。分析師把想法形式化成需求，設計師再把需求解讀回設計。這種分離是為了問責而存在的，但它慢，而且有損耗。
AI-native
兩個階段在同一次被提示的 session 裡發生。Claude 拿 intent.md 產出需求與設計規格，受組織的 skills 約束，並把疑慮之處標記出來。
前置
寫好一份 intent.md，以及把品牌、安全、合規、UX 政策寫成 skills。
基礎建設
一位有 Claude 存取權的產品負責人。不需要任何工程技能。

怎麼執行

  1. 產品負責人開一個載入組織 skills 的 session，附上 intent.md。
  2. 提示詞指向 intent.md、點名限制、並要求標記疑慮。先手動跑，再把它變成組織層級的 slash command；之後把「intent.md 在 intent 家被接受」設成觸發條件，用一個在 merge 時觸發的非互動 job 載入 skills 跑這一趟，並以 pull request 提交 spec.md。從那時起產品負責人的第一次涉入就只剩審閱。
  3. 同一位產品負責人拿規格對照原始想法：規格有沒有解決陳述的問題？intent.md 裡的開放問題被回答了，還是被往下帶了？
  4. 先處理被標記的疑慮——那些正是分析師會往上呈報的點。產品負責人在工程看到規格之前，逐一與政策負責人解決。
  5. 把 spec.md 和 intent.md 一起提交。這一對檔案記錄了「要求了什麼」與「決定了什麼」。
  6. 產品負責人決定規格與意圖是否進入 build；組織歸類為較高風險的，要諮詢技術主管。這個決定永遠由人做，而接受規格就是階段 3 plan mode 的啟動訊號。
提示詞範本（原文原句）
Read the attached intent.md and produce a requirements and design
spec for integrating it into our existing codebase. Apply the skills
available to you so the plan conforms to our brand guidelines,
security policies and UX standards. Document the spec fully as
spec.md, ready to hand to the engineering team. Describe clearly any
areas of concern, especially where you cannot satisfy contradicting
policies.

最後那句是重點：要求它明講「哪裡有互相矛盾的政策無法同時滿足」。這是把人的判斷力導向真正需要判斷的地方。

治理
政策不是幾週後在審查裡被發現，而是在規格被寫的當下就被讀取並套用。組織的 skills 作為規格的約束條件。規格本身、產生它的提示詞、以及當時生效的 skill 版本，全部記錄在版本控制裡。產品負責人簽核規格，並把被標記的疑慮路由給指定的政策負責人。
領先指標
同一個變更的 intent.md 提交到 spec.md 提交之間的時間（兩個 git 時間戳），與舊的「需求＋設計」週期相比。
落後指標
build 開始後的需求返工：數一數同個變更中，日期晚於第一份 plan.md 的 spec.md 提交次數。git log 直接給得出來。
階段 03

Build — 開發

沒有被接受的計畫就不動手。機構知識變成 agent 讀得到的檔案，護欄以程式碼的形式執行，而不是靠習慣。

這一階段有五個 play，是全篇最厚的一段。

B1 Plan mode 作為預設起手式Claude 讀 codebase 但不動任何檔案，直到你接受計畫 展開

工程師以 plan mode 起手，把階段 2 核准的 spec.md 交給 Claude，讓它反過來訪談自己，一路迭代計畫到工程師滿意為止。

傳統
工程師讀完設計就開始寫。變更要怎麼做、動哪些檔案、寫哪些測試，全留在工程師腦袋裡，最好的情況也只是一則工單留言。沒有別人審得到。審查者看到的第一個東西是完成的 diff——到那時候要返工已經很慢了。
AI-native
工作從一份書面計畫開始，由 Claude 在 plan mode 產出——這個模式下它可以讀 codebase 但不改任何東西。工程師在程式碼被寫之前修正計畫，核准版本提交成 plan.md，供後面的階段拿來對照。
前置
意圖產物（intent.md 或 spec.md）如果有的話，以及 CLAUDE.md（有幫助但非必要）。
基礎建設
有 repository 存取權的 Claude Code。

怎麼執行

  1. 工程師以 plan mode 開 session。
  2. 把 intent.md 與 spec.md 給 Claude，要一份實作計畫，指名會動到哪些檔案、工作順序、以及證明它成立的測試。
  3. 盤問這份計畫：這個變更可能弄壞什麼？哪一步風險最高？你考慮過但沒選的其他做法是什麼？
  4. 迭代到「一個從沒看過這段對話的工程師，光靠計畫就能實作」為止。
  5. 把核准的計畫提交成 plan.md。它加入稽核軌跡，階段 5 的 PR 審查會拿最終 diff 來對照它。
  6. 接受計畫，讓 Claude 實作。計畫夠紮實的話，實作經常一趟就過。
  7. 實作偏離計畫時，在同一個 commit 裡更新 plan.md。可以考慮用 hook 強制兩者同步。
plan.md
# Plan: claims status self-service (from intent.md 2026-06-02)

## Files that change
portal/src/claims/StatusPanel.tsx (new), claims-api/routes/status.py,
claims-api/tests/test_status.py

## Order of work
1. Add the status endpoint behind existing auth.
2. Panel against the endpoint.
3. Wire into the portal nav.

## Risks
The claims-core API rate-limits at 50 rps; the panel must cache.

## Proof
test_status.py covers the four claim states; screenshot matches the
approved mock.
治理
設計審查發生在任何程式碼被產生之前——那時候要改方向還只是編輯一份文件的事。plan mode 自己就強制了這件事，因為在工程師接受計畫之前 Claude 無法編輯檔案。計畫與其修訂連同「誰接受的」一起被記錄。例行變更由工程師核准，組織歸類為較高風險的送技術主管或架構師。
領先指標
第一次實作就 merge 的變更佔比；從計畫核准到 PR merge 的時間（資料在 PR metadata 裡）。
落後指標
每個變更的返工次數（同樣讀 PR metadata），以及 merge 的 diff 有多常仍然吻合已提交的 plan.md。

延伸：auto mode

Claude Code 也可以跑 auto mode——工程師核准計畫、迭代到滿意之後，Claude 逐項套用變更而不再逐次徵詢。隨著後面幾個 play 的護欄成熟（調校過的 CLAUDE.md、把政策編碼的 skills、擋掉不安全動作的 hooks、Claude 跑得動的測試套件），auto-accept 會變成例行工作的預設值：規格緊、爆炸半徑小、程式碼已被測試覆蓋。

轉變在於：從「使用者看著 agent 編輯、審查每個動作」，移向「在較長的自主 session 之後審查產物」。auto-accept 搭配 worktrees 進一步讓個人與團隊層級的平行化成為可能，而且是自主跑完整個 SDLC、閉上迴圈（階段 6）的基礎。

側欄：既有系統與「真相來源」

適用於這個流程產出的每一份產物。

既有 SDLC 流程很可能已經在追蹤這些產物了，只是不是用 markdown：工作項目在 Jira、需求在一個內建法規追溯性的工具裡、設計在 Figma、變更核准在變更委員會。這些系統很難被取代，因為稽核員與監理機關已經接受它們，而且其他團隊靠它們吃飯——所以 AI-native SDLC 必須繞著既有的東西長。

轉換時，對每一份產物指定「一個」系統作為真相來源，其他都只持有副本或連結。三種配置：

  • repo 是真相來源。markdown 產物是權威紀錄，既有系統引用 commit 裡的檔案。對工程主導的組織來說這是最乾淨的配置之一——所有紀錄在一個工具裡、一個時間戳權威。
  • 既有系統是真相來源。Jira、ServiceNow 或需求工具持有權威紀錄，markdown 是工作副本。Claude 在 session 開始時讀取紀錄，並在同一個 session 裡透過 MCP connector 把結果寫回去。
  • 連結是最低標準。所有產物註記紀錄 ID，所有既有紀錄含有 markdown 檔的 commit SHA。這是轉換期不錯的起點——代價是承認有兩個真相來源。

兩套可以並存，只要兩者之間有連結，或其中一個被宣告為真相來源。

B2 CLAUDE.md把「新人第一天需要知道的」變成 agent 每次開場都會讀的檔案 展開

CLAUDE.md 給 Claude 的是一個新加入者需要的脈絡：慣例、指令、架構，以及團隊最常看到的錯誤。原本存在人腦袋裡和 wiki 上的知識，變成 agent 在每次 session 開始時讀的檔案，由整個團隊維護，每次犯錯就迭代一次。

前置
無。
基礎建設
一個 repo、裝好的 Claude Code、以及一位很熟這個 codebase 的工程師。

怎麼執行

  1. 在 repo 裡跑 /init。Claude 會從它找到的東西產生一份起手的 CLAUDE.md。
  2. 把產生的檔案砍到只剩「新人第一天需要的」：build／test／lint 指令、真正重要的慣例、以及 Claude 一直搞錯的東西。
  3. 把 CLAUDE.md 放在 repo 根目錄並納入 git，讓全隊共用一個版本、變更像程式碼一樣被審查。
  4. 一條實用的工作規則：當 Claude 犯同一個錯第二次，修正就寫進 CLAUDE.md。
  5. 控制在一頁以內。Claude 在 session 開始時整份讀完，任何過時的內容都在白白吃掉 context。
CLAUDE.md
# Payments service

## Commands
- Build: make build
- Test: make test (unit), make itest (integration, needs docker)
- Lint: make lint (runs in CI; fix before pushing)

## Conventions
- Java 21, Spring Boot 3. No new Lombok.
- Money is always BigDecimal, never double.
- Every endpoint needs an integration test in src/itest.

## Architecture
- api/ holds REST controllers, core/ holds domain logic,
  adapters/ talks to external systems.
- Kafka events are defined in schemas/; never edit generated classes.

## Things Claude gets wrong
- Do not bump dependency versions; the platform team owns them.
- The legacy v1/ package is frozen; changes go in v2/.
治理
CLAUDE.md 受版本控制，所以 agent 依循的指令是可審閱、可稽核的。團隊慣例透過這份檔案被套用，它的變更記在 git 歷史裡，並由 code owners 在 PR 審查中核准。
領先指標
Claude 重複犯「CLAUDE.md 本該擋下」的錯誤的頻率。對 CLAUDE.md 的修正應該被追蹤在 git 歷史裡。
落後指標
新成員從加入到第一個 PR merge 的時間（讀 PR 歷史）。
B3 Skills 作為機構知識要一致套用的政策寫成 skill；屬於 CLAUDE.md 或提示詞的，不要寫成 skill 展開

Skills 是組織把機構知識可操作化的方式：指令明確、受版本控制、廣泛套用、政策改變時集中更新。

經驗法則：必須被一致套用的機構知識，寫成 skill；屬於 CLAUDE.md 或屬於一次性提示詞的東西，不要寫成 skill。

前置
不需要。有 CLAUDE.md 有幫助（它把 agent 的工作知識留在 repo 裡），但 skill 不依賴它。
基礎建設
一條有指定負責人、且有書面真相來源的政策。

怎麼執行

  1. 挑一個今天被執行得不一致的知識點：可能是安全標準、API 設計慣例，或品牌規則。
  2. 把它寫成 skill——一個含 SKILL.md 的資料夾，frontmatter 說何時觸發，body 說要做什麼。由工程師依政策負責人的真相來源撰寫，可用 Claude 協助。
  3. 把 skill 放在 repo 的 .claude/skills/<name>/ 讓它隨程式碼一起走，或透過 plugin 在整個組織散佈。
  4. 測試 skill 真的會觸發。用不同的講法要求 Claude 做相關任務，確認每次都載入。
  5. 政策變更時改 skill，並讓政策負責人簽核那次變更。
  6. 工程師會在下一次 session 自動拿到新版本。
.claude/skills/secure-api-review/SKILL.md
---
name: secure-api-review
description: Apply the API security standard. Use whenever creating or
  modifying an external-facing endpoint, reviewing API code, or
  generating an OpenAPI spec.
---
# Secure API review

When you create or change an API endpoint:
1. Authentication: every endpoint requires the gateway JWT;
   no anonymous routes outside /health.
2. Input validation: validate request bodies against the OpenAPI
   schema and reject unknown fields.
3. Audit: every state-changing endpoint emits an audit event with
   actor, action, entity and timestamp.
4. Data classification: fields tagged pii in the schema must never
   appear in logs or error messages.

Run scripts/check-endpoints.sh and include its output in your summary.
治理 — 這段是全篇最重要的細節之一

skill 是一種控制，但它是「建議性」的。它讓 Claude 很可能在寫程式的當下套用政策，但沒有任何東西強迫一個 session 遵守它。

一條「必須永遠成立」的政策，需要在 skill 背後放一個確定性的東西——例如一個會擋掉動作的 hook，或一趟在 PR 端重新檢查政策的審查。skill 讓違規變罕見，hook 讓違規接近不可能。skill 的調用被記在 session traces 裡，政策負責人像審程式碼一樣審 skill 的變更。

領先指標
從政策負責人核准政策變更，到對應 skill merge 的時間（讀 skill 資料夾上的 PR）。
落後指標
PR 審查中引用該政策的發現數，應該隨著 skill 在寫程式當下就套用政策而趨近於零。如果沒有下降，要嘛 skill 沒被觸發，要嘛它的文字已經和官方政策漂移了。
B4 Hooks 作為建置期護欄skill 是建議層，hook 是它背後的確定性層 展開

Claude 大部分的動作是實作期間的檔案編輯與 shell 指令，所以建置階段是 hooks 觸發最頻繁的地方。

建置期 hooks 可以：

  • 擋掉對受保護路徑的編輯，例如產生出來的類別或一個凍結的套件；
  • 在檔案編輯後跑格式化與 lint，讓漂移永遠不會累積；
  • 把憑證擋在 diff 之外。

任何「政策必須無例外成立」的 skill，都要用 hook 墊在後面。hook 在每一個符合條件的動作上執行，所以建置期 hooks 必須快，而且範圍要限縮在被改動的那個檔案。比較重的檢查（例如完整測試套件）屬於 commit 或 PR 那一層。

會去問人要核准的 hook，屬於階段 5 的閘門——因為在建置過程中跳出核准提示，等於把一個人放回所有平行 session 的關鍵路徑上。

B5 平行 session 與 subagent一位工程師同時推進數條工作線，工作變成掌舵與審查 展開

平行 session是另一個完整的 Claude Code 實例，在自己的 git worktree 裡跑另一個任務。每個獨立 session 彼此一無所知，唯一共享的東西是掌舵的那位工程師。

subagent 跑在單一 session 內部，是一個有自己 context window 與工具限制的受限助手，適合在多個任務中重複出現的工作，例如「驗證 app 是否如預期執行」。

平行 session 拉高一位工程師同時在飛的任務數；subagent 讓每個 session 專注在自己的任務上。工程師的工作是掌舵並審查全部。

傳統
一位工程師一次做一個任務，而且一天或一週有相當大比例花在 build、測試和等審查上。等待時切換任務是可能的，但脈絡切換累到很少有人願意這樣做。
AI-native
一位工程師同時跑數個 Claude session，各自在自己的 worktree、自己的任務上。重複的工作變成有自己 context 與工具限制的 subagent。工程師的工作轉為編排，最終轉為建造並監看迴圈。
前置
CLAUDE.md（所有 session 都讀它）。階段 4 的回饋迴圈也有幫助——session 能自己驗證工作時，需要的監督就少。
基礎建設
一個 git repository（隔離來自 worktrees），以及調校過的權限設定，讓 session 不會卡在等「組織認為安全的指令」的核准提示。

怎麼執行

  1. 工程師把工作拆成會動到不同檔案的任務，用 plan mode 的計畫去看哪裡是獨立的。共用檔案的任務放在同一個 session 裡依序做。
  2. 每個平行任務有自己的 worktree，例如一個終端跑 claude --worktree feature-auth，另一個跑 claude --worktree fix-rate-limit。worktree 是自己分支上的獨立 checkout，可以避免 session 在檔案上互撞。
  3. 兩到三個 session 是合理的起點。實務上限是「一個人能好好審查幾條線」，所以只有在審查跟得上時才加 session。
  4. 把重複的工作變成 subagent，定義在 .claude/agents/ 的 markdown 檔裡，各自有名字、何時使用的描述、以及可以碰的工具。例子：主 agent 完成後負責砍掉多餘複雜度的 code simplifier；跑起 app 並檢查行為的 verifier；探索 codebase 並回報、不污染主 context 的 researcher。定義要進 git，讓全隊共用。
.claude/agents/verifier.md
---
name: verifier
description: Runs the app and checks the change works before the session
  reports done
tools: Bash, Read
---
Start the app with make run. Exercise the changed behavior and the two
nearest neighboring flows. Report what you ran, what you saw, and any
behavior that does not match plan.md. Do not fix anything; report only.
治理
更多 session 代表更多產出，所以控制必須來自 repo 裡的設定。放在那裡的 hooks 與權限設定會套用到所有 session，而 session 做了什麼會被記錄並歸屬到執行它的那位工程師身上。
領先指標
在審查品質維持的前提下，每位工程師的並行 session 數（從 OpenTelemetry 匯出計算），以及一天當中花在掌舵而非等待的比例。
落後指標
每位工程師每週 merge 的變更數，要與返工率一起讀（返工率由 PR 歷史決定）。
階段 04

Test — 測試

每個 session 在人看到之前先檢查自己的工作；而那份「操縱 agent 的設定」本身，也要像它產出的程式碼一樣被回歸測試。

T1 給 Claude 一個回饋迴圈測試、build、截圖比對——它自己修完再交出來 展開

永遠給 Claude 一個能驗證自己工作的方法，不論是測試、build 還是截圖差異。session 在工程師看到之前，先檢查自己的工作、修自己的錯。

回饋迴圈不要跟 verifier subagent（階段 3）搞混。回饋迴圈貫穿整個任務，跑幾次由工作決定；verifier subagent 是把最終檢查打包起來的一種方式——在 session 認為工作完成後，用一個全新的 context window 跑一次，這樣結論就不會被「產生這段程式碼的那些假設」染色。

傳統
「程式碼能動」這個訊號來得很晚。CI 是幾分鐘後，測試人員是幾天後，生產環境是幾週後。當程式碼是 agent 產出的，訊號晚就意味著要有一個人去檢查它的全部輸出——而那個人就變成瓶頸。
AI-native
session 被給了一個在人看到之前檢查自己工作的方法。跑測試、跑 build、拍截圖。Claude 一直迭代到檢查通過，所以到工程師手上的東西已經通過了。設定這個迴圈是跑 session 那位工程師的責任。
前置
無。
基礎建設
一套測試與一個 build，各自能用一行指令在本機跑起來。UI 工作則必須讓 Claude 看得到結果——瀏覽器工具，或透過 MCP 接上的截圖工具。

怎麼執行

  1. 如果今天檢查工作要跑一串指令＋一些環境知識，把它包成單一目標，例如 make test 或 npm test，失敗時回傳非零。
  2. 在 CLAUDE.md 的 Commands 區塊，列出每個指令並附一個健康輸出的範例。
  3. 陳述一個目標並且讓它可量化，這樣 Claude 不用問你就能自我檢查。例如：「test_status.py 的所有測試通過」、「截圖吻合附上的 mock」、「端點回傳 200 且含新欄位」。
  4. 修 bug 時先寫失敗的測試。請 Claude 把 bug 重現成一個測試、跑它、確認它以你預期的理由失敗。提交那個測試。然後才請 Claude 讓它通過、且不得編輯測試——用最後一步的 test-file hook 強制這個限制。一個在修復之前就存在、而且 agent 改不動的測試，就是 bug 已消失的證明。
  5. UI 工作用視覺檢查閉環：給 Claude 瀏覽器或截圖工具、給它 mock，讓它迭代。實作、截圖、比對、調整。兩到三輪是正常的，而且每一輪結果應該更好。
  6. 把驗證變成「完成」的一部分。指令寫在 CLAUDE.md 裡：回報任務完成前先跑測試，並附上輸出。
  7. 最後，迴圈本身需要被保護——因為一個在修程式碼的 agent，絕不能有能力削弱針對那段程式碼的檢查。一個在修復任務期間擋掉測試檔編輯的 hook 就做這件事。替代方案是在審查時檢查 diff，並拒絕任何動到測試的變更。
CLAUDE.md — 驗證區塊
## Verifying your work

- Build: make build (must finish with "Build succeeded")
- Test: make test (all green; never skip or delete a failing test)
- Lint: make lint (zero warnings)

Run all three before reporting any task complete, and paste the output.
If a test fails, fix the code, not the test.
治理（原文在這裡拆成四問，值得照抄）
  • 強制了什麼：回報完成之前必須驗證；修復任務期間禁止 agent 編輯測試檔。組織要保證時，兩者都實作成 hooks。
  • 證據是什麼：make test 的實際輸出、build log，或 Claude 跑過並貼上的截圖差異——證據來自工具鏈，不是來自宣稱。
  • 記在哪裡：session transcript（由 OpenTelemetry 匯出轉發到組織的可觀測性堆疊），以及 PR 的 check run，審查者與日後的稽核員都看得到。
  • 誰核准：審 PR 的 code owner——他可以專注在意圖與風險上，因為機械性的證據已經附上了。
領先指標
agent 撰寫的變更的首次 CI 成功率（CI 系統本來就支援）。
落後指標
每個 PR 的審查時間（讀 PR metadata），應隨著測試接手了審查者原本抓的東西而下降；以及事故追蹤系統裡的變更失敗率。
T2 CI 裡的持續 evalsagent 的設定變了，就要回歸測試——它是 AI-native 版的階段閘 QA 展開

Evals 是階段閘 QA 的 AI-native 對應物。實務上是一套只要 agent 的設定改變就會跑的測試：換了新模型、改寫了提示詞，eval 套件會告訴你 agent 是否還維持同樣水準。

evals 應該被視為活的套件。隨著模型變強，曾經有鑑別力的案例會失去鑑別力，必須從持續監控中補進新案例。

依使用情境不同，有些團隊會偏好用固定節奏離線跑，而不是每次變更都跑。下面的步驟寫的是「持續」版本。

前置
CLAUDE.md 與回饋迴圈（T1）。
基礎建設
能非互動執行 Claude Code 的 CI，以及一把有 eval 執行預算的 API key。

怎麼執行

  1. 平台工程師從近期工作中蒐集 20 到 50 個真實任務，連同它們的預期／可接受結果。
  2. 把每個任務寫成一個 eval：提示詞 ＋ 定義「可接受」的檢查（測試通過、lint 乾淨、行為不變、政策被遵守）。
  3. 套件在 CI 中非互動執行，按排程跑，並在 CLAUDE.md、skills 或 hooks 有任何變更時跑——因為那些設定操縱著 agent，理當享有程式碼等級的回歸測試。
  4. 把設定變更 gate 在結果上。一個讓通過率下降的 skill 變更，要先被審查才能 merge。
  5. 每一次生產事故都變成一個 eval，由擁有該事故的團隊撰寫，並永久留在套件裡作為回歸測試。
.github/workflows/agent-evals.yml
name: Agent evals
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']
  schedule:
    - cron: '0 2 * * *'
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g @anthropic-ai/claude-code
      - name: Run eval suite
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          for eval in evals/*.json; do
            claude -p "$(jq -r '.prompt' $eval)" \
              --allowedTools "Read,Edit,Bash(make test)" \
              --output-format json > result.json
            ./evals/check.sh "$eval" result.json
          done

注意 paths 那兩行：觸發條件是 CLAUDE.md 與 .claude/**——這正是「把 agent 設定當程式碼對待」的具體落點。

治理
Evals 給了 QA 一個跟得上 agent 產出速度的閘門。通過率門檻以 merge check 的形式強制執行，每次執行都被記錄以便跨時間比較，而擁有該設定變更的團隊負責核准它。
領先指標
eval 通過率隨時間的變化（套件每次執行都回報），以及一次生產事故要多久才變成一個常駐 eval。
落後指標
在 CI 抓到的回歸數，對比在生產環境發現的回歸數（來自事故追蹤系統）。
階段 05

Deploy — 部署

審查雙向進行，治理在 agent 動作的當下被強制。agent 做完通往生產閘門之前的所有事，然後一步都不越過那道閘門。

R1 PR 審查迴圈裡的 AIClaude 既給審查也收審查；人的注意力往上移一層 展開

Claude 既給審查也收審查。它依組織政策審查進來的 PR，也處理自己 PR 上收到的審查意見。這讓工程師在 PR 審查時專注於行為——歸結起來就是判斷意圖與風險。

傳統
審查產能是照人的產出量規劃的。一個 PR 等著審查者把它整份讀完，審查品質隨審查者當下的負載浮動，作者一邊追人一邊看著待審佇列變長。
AI-native
所有 PR 都得到一組完全相同的審查趟數，發現依嚴重度排序。人的注意力上移一層：這個變更做的是不是計畫想做的事？風險可不可以接受？
前置
階段 3 更新過的 CLAUDE.md；若審查趟數要強制書面政策則需要 skills；已定義的 subagents。
基礎建設
裝好 Claude 整合的 repo：由 admin 啟用的託管版 Code Review（research preview），或在自家 CI 跑的 claude-code-action；必要時模型呼叫走 AWS Bedrock、Google Vertex 或 Microsoft Foundry。另外，要求 code owner 核准的分支保護政策也很值得設。

怎麼執行

  1. 託管版 Code Review 服務是最快的起點。需要掌控 pipeline、或想讓 API 呼叫走自家雲端合約時，才用 claude-code-action 在自家 CI 跑。
  2. 技術主管把審查政策寫成 repo 根目錄的 REVIEW.md，切成組織在意的幾趟：bug 與邏輯錯誤；安全與漏洞；對照 spec.md、plan.md 與設計原則的合規性。REVIEW.md 同時定義什麼算 Important、什麼只是 Nit，以及什麼要跳過。
  3. 技術主管設定人為門檻。審查發現本身不會核准或封鎖 PR，分支保護仍然要求 code owner 核准。想以發現數 gate merge 的平台工程師，可以讀 check run 發布的機器可讀嚴重度統計。
  4. 當審查者或作者在審查留言裡 tag @claude，Claude 處理該留言並推送修正，PR 討論串同時記下請求與變更。對 Claude 自己開的 PR，可以更進一步讓 Claude 一路顧到 merge：團隊把這個迴圈包成自訂 slash command，掃過 PR 上未解決的審查留言與失敗的檢查、處理它們、推送修正，直到 PR 全綠、只剩 code owner 核准。
  5. 審查發現要回流到 CLAUDE.md。當審查第二次標出同一個錯誤，修正就在那次審查中寫進 CLAUDE.md；因為審查會讀 CLAUDE.md，這個錯誤從下一個 PR 起就會被抓到。審查也會標出「這個變更讓 CLAUDE.md 過時了」。
  6. 每月一次，技術主管調校設定：替發現打分讓審查者變強，並在 REVIEW.md 裡限制 Nit 的數量。產生出來的路徑、以及 CI 已經強制的東西，都排除掉。
REVIEW.md
# Review instructions

## Passes
Run three passes and tag each finding with its pass:
- Bugs: logic errors, broken edge cases, subtle regressions
- Security: injection risks, authentication gaps, PII in logs
- Compliance: the change matches spec.md, plan.md and our design principles

## What Important means here
Reserve Important for findings that would break behavior, leak data
or breach a policy. Style and naming are nits.

## Cap the nits
Report at most five nits per review; summarize the rest as a count.

## Do not report
Generated files under src/gen/ and anything CI already enforces.
治理
職責分離被保住了，因為寫程式的那個 agent 沒有任何途徑核准它。REVIEW.md 裡的審查政策套用到所有 PR，而發現、修正、評分與核准全部記錄在 PR 歷史裡——所以 PR 本身就是稽核紀錄。核准來自人，透過分支保護，並由審查發現提供資訊。
領先指標
到首次審查的時間（應降到分鐘級），以及「沒有人碰分支就被解決」的審查留言佔比，資料直接存在 git 上。
落後指標
merge 前抓到的缺陷與漏洞數，對比逃到生產環境的數量（來自 PR 歷史與事故追蹤系統）。
R2 Hooks 作為核准閘hook 除了 allow／block，還可以「ask」——暫停動作直到指定的人核准 展開

建置階段把 hooks 當成護欄，在沒有人涉入的情況下允許或封鎖動作（階段 3）。hook 也可以「問」——暫停動作直到某位特定的人核准，這正是發布 gating 需要的東西。

這個 play 放在階段 5 是因為發布閘是最清楚的案例，但 hooks 並非部署專屬：它們在 Claude 動作的任何地方執行。例如在階段 3 擋掉「沒有變更工單就編輯 migration 與基礎設施」，或在階段 4 阻止 agent 在修復任務中編輯測試檔。

前置
無。
基礎建設
一份書面清單，列出變更流程要求的所有核准。

怎麼執行

  1. 工程領導層會同變更管理與合規，列出哪些人為核准閘必須存活：變更管理簽核、發布授權、受保護路徑的編輯等。
  2. 平台工程師把每個閘門表達成一個 hook——一個在 Claude 動作前執行、可以 allow／ask／block 的腳本。
  3. 團隊 hooks 放在 git 裡的 .claude/settings.json；不可協商的 hooks 放在由平台或 IT 管理員擁有的 managed settings 裡，個別工程師關不掉。
  4. 封鎖必須自己解釋自己：當 hook 擋下一個動作，理由與取得核准的途徑要出現在 Claude 的輸出裡。

#!/bin/bash
# Production deploys require a named release authorization
cmd=$(jq -r '.tool_input.command' < /dev/stdin)
if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
  if [ -z "$RELEASE_APPROVAL" ]; then
    echo "Production deploys need a release authorization." >&2
    exit 2   # exit 2 blocks the action; the message goes to Claude
  fi
fi
exit 0

設定它擋住的是什麼
permissions.deny把祕密擋在 agent 的 context 之外，並封鎖經由工具的任意網路外連。
permissions.allow預先核准安全的內圈迴圈，免得 deny 清單變成提示疲勞。
disableBypassPermissionsMode
+ allowManagedPermissionRulesOnly		沒有任何工程師、專案檔或命令列旗標能把規則放寬。
sandbox補上權限補不到的洞。對 WebFetch 的工具層 deny，擋不住一個 shell 指令連上網路；OS 層的網域白名單直接封鎖外連。
failIfUnavailable
+ allowUnsandboxedCommands		讓 sandbox 成為閘門：sandbox 起不來時 Claude Code 拒絕啟動，而在 sandbox 內失敗的指令不能拿到外面重試。
credentials補上 deny 規則留下的洞。permissions.deny 管的是 Claude 的檔案工具，但一個沙箱化的 shell 指令預設仍讀得到 ~/.ssh 或 ~/.aws/credentials；這個區塊拒絕那些讀取，並把指名的祕密從每個沙箱指令的環境變數裡剝掉。
allowManagedHooksOnly本 play 的核准閘是唯一會執行的 hooks，本機沒有任何東西能增補或取代它們。
disableSideloadFlags
+ strictKnownMarketplaces		工程師機器上的每個 skill、agent、hook 與 MCP server，都是經由組織核可的 plugin marketplace 進來的，絕不會來自家目錄。
allowManagedMcpServersOnlyagent 的工具面變成一份由平台團隊擁有的白名單。
requiredMinimumVersion低於核可下限的版本直接拒絕啟動，所以控制是由「組織真的評估過的建置」在執行。

原文特別聲明：把上面當成一個要裁剪的起點，而不是照抄的建議。每一條 deny 都在跟能力做交換，正確的平衡取決於該 repo 的資料分級。

治理
Hooks 就是核准閘。閘門條件每一次、對每一個人都被執行。allow 與 block 的決定連同時間戳被記錄。閘門同時定義「什麼算核准」——是一張核准過的變更工單，還是發布經理的簽核。
領先指標
每一道核准閘上的等待時間。每個 hook 決定都會帶時間戳與 allow／block 判定寫進 OpenTelemetry 匯出，所以等待是逐閘可見的。
落後指標
導入 hooks 前後，抵達生產環境的閘門違規數（來自事故追蹤系統）。
R3 CI/CD 整合與部署agent 可以做到生產閘門為止，而且不能越過它 展開

在 CI/CD pipeline 內部非互動執行 Claude Code，把執行沙箱化讓長時間執行的 agent 安全運作，透過 MCP 整合暴露部署能力，並且在 agent 真的需要之前就先演練好 rollback 路徑。

傳統
Pipeline 跑確定性腳本，任何需要判斷的事就等人。例如分流一個 flaky test、寫 changelog、搞清楚 build 為什麼掛了。部署與 rollback 是人在壓力下照著跑的 runbook。
AI-native
Claude 在 pipeline 內非互動執行那些需要判斷的步驟，跑在沙箱裡、帶著範圍受限的憑證。部署工具透過 MCP 暴露給 agent，所以寫了並測了這個變更的同一條工作流，也可以把它送上線、也可以把它退回來，全部在組織依環境定義的閘門之內。
前置
PR 審查迴圈（R1）與 hooks 核准閘（R2）——閘門必須先存在，自動化才不會只是把東西加速衝過去。
基礎建設
裝有 claude-code-action 的 CI 平台，或任何能呼叫 claude -p 的 runner；模型存取走 API，或在流量必須留在自家雲端合約時走 Bedrock／Foundry／Vertex；部署目標的 MCP servers；一個給 agent job 用、預設不持有生產憑證的沙箱設定檔。

怎麼執行

  1. 平台工程師從唯讀的判斷步驟開始。在 pipeline job 裡用 claude -p 分流失敗的 build、摘要 flaky test，或起草 changelog。
  2. 把寫入步驟加在既有閘門之後：修 lint、更新產生的文件、透過 @claude 提及處理審查留言。agent 寫的任何東西都以 PR 的形式經過分支保護，agent 沒有推上 main 的途徑。
  3. 執行要沙箱化。agent job 跑在網路政策下的容器裡，持有短期、範圍受限的 token，預設不持有任何生產憑證。
  4. 透過 MCP 暴露部署。deploy、status、rollback 變成工具，依環境限定範圍——於是 agent 的部署權力是一份白名單，而不是一個帶著憑證的 shell script。
  5. 依環境分層自主權。開發環境 agent 自由部署；生產環境 agent 準備發布、由發布經理授權，並由 hook 強制生產閘門；staging 落在中間。
  6. Rollback 應該是整條 pipeline 中被演練得最熟的路徑：一個 agent 跑得動的單一指令，而且定期在 staging 演練。階段 6 的閉環 play 會在控制帶被突破時呼叫這個 rollback，所以它必須事先被證明過。

治理

治理原則就是一句話：agent 可以動作到生產閘門為止，而且不能越過它。

  • 分支保護把 agent 寫的任何東西都變成 PR，沒有直達 main 的路。
  • 生產部署 hook 封鎖發布，直到一位指名的發布經理授權。每一次非互動執行都以 agent 自己的身分行動，所以 pipeline log 分得清「agent 做了什麼」與「觸發它的工程師做了什麼」。
  • 依環境的權限分層，設定 agent 在抵達閘門之前能做到什麼程度。
領先指標
不需要 call 人就完成分流的 pipeline 失敗佔比（來自 CI/CD pipeline logs）。
落後指標
DORA 指標——CI 系統與部署工具本來就會發出這些數據。
階段 06

Maintain — 維運

迴圈在這裡閉合。一個觸發器在沒有任何人在呼叫路徑上的情況下叫起 Claude，而它發現的東西以 intent.md 的形式重新進入流程。

前面五個階段都還需要人去啟動第一步。階段 6 把焦點轉到自主執行：一個持續執行的監控 agent，可以在一張 bug 工單被開出來時建立 intent.md，然後一路流過需求、計畫、開發、測試與審查。它跑在 headless，階段與階段之間有一道獨立的信心閘——一個確定性檢查或一個對抗性的審查 agent——決定前一階段的產出是繼續往下，還是升級給人。

傳統
維運是被動階段。所有工單或事故都在等一個人去動作、去重啟流程。凌晨三點的告警可能被漏掉，一張工單可能躺在待辦裡直到有人撿起來，而事後檢討的行動項目在下一場火燒起來時，可能根本沒進到 codebase。
AI-native
一個觸發器（控制帶被突破、一張工單、一則頻道訊息或一個排程）在沒有人在路徑上的情況下叫起 Claude。Claude 診斷、只透過受閘門管制的途徑動作，並把發現寫成 intent.md，接著走完前述所有階段。人負責分流與審查那份工作，不再需要啟動它。
M1 閉環：控制帶與 bands.yaml偵測完全確定性，模型只在破線後才被叫進來 展開

一個確定性腳本盯著生產環境，在控制帶被突破時叫起 Claude。監控突破是「迴圈自主執行」這個模式最好懂的例子；本階段最後的 Claude Tag 一節則涵蓋工作經由其他管道抵達的情形。

前置
intent.md（給迴圈一個結構化的輸出去重啟流程）、Claude 加速的 PR 審查、hooks 作為動作邊界，以及 CI/CD 的 rollback 路徑（最高自主層級會呼叫它）。
基礎建設
偵測腳本查得動的指標儲存（Prometheus、CI 系統的 API 或同類），repo 的讀取權限，以及在 CI 中非互動執行 Claude Code 的方式，或用 Agent SDK 做一個接收 webhook 的服務。

怎麼執行

  1. 服務負責人或平台工程師挑一個有穩定滾動基線的指標：CI 測試失敗率、部署後的 5xx 率，或 PR 週期時間。
  2. 寫偵測腳本，通常是滾動視窗上的平均值與標準差，加上規則（Western Electric 或類似），讓控制帶既抓得到尖峰也抓得到緩慢漂移。腳本受版本控制、有單元測試，而且偵測完全保持確定性，沒有任何模型涉入。
  3. 回應層級定義在受版本控制的設定裡（下面的 bands.yaml）。1σ 只記錄；2σ 以唯讀方式叫起 Claude 診斷；3σ Claude 可以動作，但只能透過開 PR 進入審查閘，或觸發預先核准的 runbook。
  4. 觸發層可以是 GitHub／GitLab 的排程 workflow、既有監控堆疊發出的 webhook，或網路內的 Cron Job。Claude 無狀態執行——CI runner 上的非互動步驟，或沙箱容器裡的 Agent SDK 服務。因為執行是無狀態且非互動的，一個迴圈可以在沒有任何人啟動的情況下開始與結束。
  5. agent 把診斷寫成階段 1 格式的 intent.md，涵蓋異常與其證據、提議的成果、受影響的系統，以及任何開放問題。從那裡開始，這個發現就跟其他任何東西一樣走完整條流程。
  6. 服務負責人或 on-call 工程師分流佇列，把面向產品的發現路由給產品負責人。現在修、排程、或駁回。而駁回會回頭調校控制帶、降低噪音。
  7. 修復上線時，替這次事故加一個 eval（見 T2），確保這類問題日後有防護。

1σ
log — 只記錄。模型完全沒被叫起來。
2σ
diagnose — 叫起 Claude，唯讀。工具限定 Read, Grep, Bash(gh run view *)。
3σ

治理
層級邊界由受版本控制的設定強制，權限與 managed settings 拒絕生產環境存取。叫起、發現與分流決定都帶時間戳被記錄。服務負責人分流並核准發現，產生的變更走一般 PR 審查閘，而 agent 能觸發的 runbook 都是事先核准過的。
領先指標
從控制帶突破到分流佇列裡出現一份 intent.md 的時間，對比舊的「事故到事後檢討行動」時間。偵測腳本的 log 有突破時間戳與層級。
落後指標
發現最終變成 merged 修復的比例（分流佇列對 PR 歷史），以及同類事故的重複次數——它應該隨著修復把案例加進 eval 套件而下降。

三個具體例子

  • CI 測試失敗率突破 3σ 時，agent 隔離該 flaky test 或開一個 revert PR，由審查閘決定。
  • 部署後 5xx 率突破 3σ 且該時間窗內有一次部署時，agent 觸發既有的 rollback pipeline。
  • PR 週期時間觸發漂移規則時，agent 寫一份報告給工程領導層——這顯示這套裝置對流程指標跟對生產指標一樣管用。
M2 週期性程式碼庫掃描掃描結果會過期兩次：程式碼會變，模型也會變 展開

一次安全掃描，是「在某個特定模型之下、對某個 codebase 的一個時間點陳述」。而這兩半都會過期：程式碼每週都在變，而每一代模型都會找到上一代漏掉的漏洞。

AI-native 的答案是：按排程執行掃描，呼叫路徑上沒有人，並把它找到的東西送進跟其他任何程式碼變更相同的閘門。

Claude Security 是這種排程掃描的託管形式。連上 GitHub repository，掃描在 Anthropic 的基礎設施上以 Claude Mythos 5 執行，每個發現在被回報之前都經過驗證，並附上信心評分。建議的修補在 Claude Code on the web 中審閱與套用。組織拿得到發現，而不需要自己取得模型的存取權。

傳統
安全掃描是一個事件：在發布或稽核前啟動一次掃描。報告進到追蹤系統，待辦被人工消化到下一次事件為止。中間寫的程式碼，就靠 PR 審查抓到什麼算什麼。
AI-native
掃描按排程對每個連上的 repository 執行，用當前最強的模型，發現在任何人讀到之前先被驗證。每個發現的處理方式跟控制帶突破一樣：塞得進一個 PR 的修復走審查閘，更大的就變成 intent.md。覆蓋率的日期從最後一次執行算起，不是從第一次。
前置
PR 審查閘與 hooks 核准閘（階段 5），讓發現像其他變更一樣走審查；以及階段 1 的 intent.md 格式，給塞不進單一 PR 的發現用。
基礎建設
Claude Security 對 Claude Enterprise 組織開放公開 beta。需要在目標 repository 上安裝 Anthropic GitHub App（雲端託管的 github.com）、啟用 Claude Code on the Web、開啟 Extra Usage 並設定支出上限、給執行掃描的人 premium 席位，並由管理員在 claude.ai/admin-settings/claude-code 打開該功能。掃描以 Mythos 5 費率按用量計費，所以支出上限要與 repository 的規模與數量相稱。

怎麼執行

  1. 安全負責人連上 repositories，並依 repo、服務或團隊把它們組織成 projects，讓發現的歸屬從一開始就清楚。
  2. 對最關鍵的 repositories 跑第一次完整掃描，包含那些已經被其他工具或更早的模型掃過的。把第一次掃描當作基線——它很可能會在被視為乾淨的程式碼裡挖出東西。
  3. 逐 project 設排程。積極開發中的服務，每週是合理的預設值；repository 很大或很混雜時，把掃描範圍縮到某個目錄或分支。
  4. 拿著信心評分分流發現。駁回時要填理由，讓駁回被記錄下來，同一個發現才不會在下次執行時又變成新的。
  5. 對於有邊界的發現，在 Claude Code on the Web 開啟建議的修補、審閱它，然後像其他任何變更一樣送進 PR 審查閘。提出修復的那個 agent 沒有任何途徑核准它。
  6. 對於比一個修補更寬的東西——架構弱點，或跨服務重複出現的模式——用階段 1 的格式寫成 intent.md，從 Plan 開始跑。
  7. 修復發布到生產環境後，替該漏洞類別在 eval 套件（T2）加一個 eval，讓操縱 agent 的設定從此對這個類別受測。
  8. 用 CSV 或 Markdown 匯出發現，或用 webhooks，讓組織既有的追蹤與稽核系統繼續當紀錄系統——稽核員本來就在那裡找它們。
治理
掃描在組織的管理控制之下執行：連上哪些 repository、誰持有掃描席位、支出上限，都是集中設定的。每個發現都有驗證結果與信心評分，每次駁回都有理由，所以掃描歷史本身就是一份稽核紀錄——記錄了什麼被找到、被修好、以及被有意識地接受了。修復經由 PR 審查閘與分支保護抵達生產環境，而不是從掃描本身。Claude Security 是既有靜態分析與相依套件掃描的補強：確定性檢查留在 CI，模型驅動的掃描負責那些檢查抓不到的、依賴脈絡的漏洞。
領先指標
已排程的 repositories 佔比，以及從發現被回報到其修補進入 PR 審查閘的時間（讀掃描歷史與 PR metadata）。
落後指標
排程掃描找到的漏洞數，對比在生產環境或由外部回報發現的（來自事故追蹤系統）；以及已跑過數輪的 repository 上「每次掃描的發現數」趨勢——它應該隨著修復與 evals 累積而下降。
M3 Claude Tag：讓 Claude 站上 on-call頻道就是稽核軌跡 展開

事故也會經由其他管道抵達，例如 Slack 或 Teams 這類工作通訊軟體。事故可能長得像「晚上十點在事故頻道裡一則要求緊急修復的訊息」——現在它可以被立刻動作。

Claude Tag（目前在 Slack 上公開 beta）讓 Claude 以自己的身分成為那些頻道的成員，於是每一起新事故都有一個第一線回應者，而回應本身成為迴圈與未來事故的記憶。

對話與機構知識留在頻道裡，頻道裡的任何人都能引導與執行回應。任何團隊成員都可以即時測試假設、探索新選項、進行調查，而頻道歷史為可稽核性再加一層。透過 MCP 存取，Claude 驗證指標已回到基線並在討論串中確認，然後把事後檢討寫進一份受版本控制的 lessons 檔案，供未來的調查讀取。

事故不是 Claude Tag 唯一撿起來的工作。經由 MCP 在一張工單上被 tag、或在頻道裡被詢問時，Claude 以同樣方式分流工作：小而邊界清楚的修復，以 PR 的形式經過審查閘抵達；更大的則寫成 intent.md 進入階段 1——迴圈從這一刻開始自己餵自己。

頻道就是稽核軌跡：請求、診斷、人的授權與修復，全都留在事故被處理的那個地方。

Anchorline 已經比 playbook 更嚴的一處

原文在 R1 的治理段寫的是「寫程式的那個 agent 沒有任何途徑核准它」——這是人／agent 粒度的職責分離。Anchorline 的 authorAgentFamily 把粒度再降一層：同一個 agent 族系撰寫的文件，不能由同族系核准。GitHub 的 CODEOWNERS 與分支保護只認人不認族系，抓不到這一類。這是 Anchorline 目前對外最有辨識度的機制，也剛好是這份 playbook 沒有寫進去的東西。

M1 閉環無。UAT 失敗、gate 未過、PR 失敗，目前都停在畫面上等人看。缺口這是最大的一塊，也是最像 Anchorline 該做的事。它已經握有全部四種訊號的錨點，只差最後一步：讓「UAT 某題失敗」或「治理鏈出現違規」自動生成一份帶錨點的 intent.md 草稿，丟回 P1。做到這裡，Anchorline 才從「看板」變成「迴圈」。
M2/M3 掃描與 on-call無。缺口對單人使用情境優先度最低，且高度依賴 Claude Enterprise。先不做，但把「發現 → intent.md」的入口先留好——那個入口跟 M1 是同一個。

三個結構性判斷

  1. Anchorline 的鏈少了最前面一段。playbook 的鏈是 intent → spec → plan → diff → PR → incident；Anchorline 的鏈是 PRD → gate → 簽核 → openspec → commits → PR → release。從 PRD 起手，等於默認「已經有人把想法寫成規格了」——而那正是傳統 SDLC 最慢的一段。補上 intent 層，是投報率最高的一步，也最便宜。
  2. 迴圈沒有閉合，所以它現在是一條線。圖 02 的虛線在 Anchorline 上是斷的。四種訊號（UAT 失敗、gate 違規、PR 失敗、release 異常）都已經有錨點，缺的只是「自動寫回一份意圖」。這一步做完，README 上那句「一條治理鏈」才會真的變成迴圈。
  3. 操縱 agent 的設定，本身沒有被治理。CLAUDE.md、skills、hooks 決定了 agent 的行為，但它們的變更不在稽核軌跡上。對一個主打「證明 agent 做的事被治理過」的產品來說，這是定位上的漏洞而不只是功能缺口：治理了產出，沒治理產出者的設定。

幾個容易讀漏的地方

  • skill 是建議，hook 才是強制。把「一定要成立」的政策只寫成 skill，等於沒有控制。
  • 核准提示不要放在建置期。它會把一個人放回所有平行 session 的關鍵路徑上——這正是你想消滅的瓶頸。
  • 偵測必須是確定性的。模型只在控制帶被突破之後才被叫進來，不參與判斷有沒有破線。
  • 修程式碼的 agent 不能改測試。否則回饋迴圈會自己把自己拆掉。
  • 每個產物指定一個真相來源。repo、既有系統、或至少互相連結——三選一，不要含糊。
  • 「每人每週 merge 數」不能單獨看。原文明確要求它和返工率一起讀。
