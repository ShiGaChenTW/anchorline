# PRD 產品需求文件範本（入門精簡版）

> 出處：張家惟 Evan Chang〈入門 PM 都要寫的產品需求文件 — PRD 基礎手冊｜EP86〉，《產品思維的創意想像》，2025-04-03（更新 2025-03-31）
> https://vocus.cc/article/67eab3e1fd89780001b3cd22
>
> 這份範本把該文第二章的六段架構轉成可填寫骨架，並把第三章的撰寫原則、第五章的四個失敗案例做成自檢清單。
>
> 原文的核心立場：**PRD 是一份「可交付的思考歷程」，不是說明書，也不是作文比賽。**
> 判斷一份 PRD 夠不夠好，看它能不能回答三個問題——
> 1. 為什麼要做這件事（目標）？
> 2. 要怎麼做、做成什麼樣（規格）？
> 3. 成功的標準是什麼（驗收標準）？
>
> 能用團隊看得懂的語言回答這三題，就完成八成任務。寫到 50 頁不等於完整。
>
> 與 `TEMPLATE-prd.md`（UIUX 兼 PM 的七段設計文件集合）的差別：這份更精簡，多了「要不要寫」的前置判準與競品分析，
> 少了心智圖、字串表、原型集中管理那幾節。小需求用這份，完整產品規劃用那份。
>
> 標題採 `## N. 標題` 編號格式，可直接匯入 Anchorline 的「整份 PRD 範本」。

## 0. 要不要寫這份 PRD

動筆前先過這一關。不是每個需求都值得一份長文件——依**需求顆粒度**決定。

**要寫 PRD**（原則：新頁面／新邏輯／新機制）

- [ ] 新型需求，需要釐清邏輯（例：AI 生成商品敘述——要釐清 input 來源、觸發時機、output 格式）
- [ ] 既有功能但有迭代新邏輯（例：會員制度調整、訂單流程重構——要界定新的邏輯機制）

**不用寫 PRD，直接開 Ticket 即可**（重點是修改工單記錄清楚）

- [ ] 前端介面顯示：按鈕調整、文案修正、增加 Tooltips
- [ ] 後端欄位調整：增加欄位限制、增加阻擋條件
- [ ] 特殊開關設定：開啟某個配置
- [ ] 日常維運處理：壓資料、刪資料

## 8. 送出前自檢

**撰寫原則（原文第三章）**

- [ ] 先說動機——開頭講的是「為什麼」，不是規則細節
- [ ] 流程示意——用了條列與示意圖，沒有大段文字牆
- [ ] 明確標準——沒有任何「適度」「盡量」「合理」這類模糊字眼
- [ ] 版更記錄——每次變更都有日期與備註
- [ ] 彈性心態——寫的細節程度符合這個團隊的習慣，不是為了格式而寫

**四個常見失敗（原文第五章）**

- [ ] 沒有只寫「照 Figma 做」就交差——觸發條件、輸入資訊、輸出格式都補齊了
- [ ] PRD 與 Figma 的規則已逐條比對過；若有不一致，已註明以哪份為準
- [ ] 每個流程的例外狀況都寫了（timeout、輸入錯誤、載入異常、資訊不足）
- [ ] 每個功能都有驗收標準，RD 能自驗、QA 能據以展開測試
